# Giải thích `SecurityConfig` — OAuth2 Login với Spring Security

## 0. Vì sao file này "ngắn mà khó hiểu"?

`SecurityConfig` chỉ khoảng 60 dòng, nhưng đọc xong vẫn không hiểu "sao nhiêu đây mà chạy được cả luồng OIDC". Lý do:

> Phần lớn cơ chế OIDC/OAuth2 **không nằm trong file này**. Nó nằm ở các **bean và filter mà Spring Security tự tạo ẩn** (endpoint chuyển hướng, filter callback, kho lưu token theo session, bộ resolve tham số controller...). `SecurityConfig` của chúng ta chỉ làm nhiệm vụ **bật các thứ đó lên và tùy biến vài chỗ**.

Giống như tảng băng trôi: code bạn thấy là phần nổi, cơ chế thật là phần chìm.

```
      SecurityConfig  (phần NỔI — bạn viết, ~60 dòng)
 ─────────────────────────────────────────────────────
      Bean & Filter Spring tự tạo  (phần CHÌM — cơ chế thật)
```

Tài liệu này đi theo 3 tầng:
1. **Tầng 1** — Các thành phần **HIỆN** trong `SecurityConfig` và vai trò của chúng.
2. **Tầng 2** — Các thành phần **ẨN** do Spring auto-config, mà config của ta móc vào.
3. **Tầng 3** — Chúng phối hợp ra sao trong **từng chức năng** của dự án.

---

## 1. Bức tranh tổng thể

Có 3 nhóm thành phần. Đọc từ trên xuống: nhóm trên **cung cấp dữ liệu / được dùng bởi** nhóm dưới.

```
NHÓM A — Spring Boot tạo từ file cấu hình
┌────────────────────────────────────────────────────────────────┐
│ application.properties                                         │
│        │                                                       │
│        ▼                                                       │
│ ClientRegistrationRepository                                   │
│ (lưu cấu hình OAuth2 Client của Google: client-id,             │
│ client-secret, scope; các endpoint OAuth2/OIDC được            │
│ Spring Boot tự bổ sung từ CommonOAuth2Provider.GOOGLE)         │
└────────────────────────────────────────────────────────────────┘
                         │
                         ▼

NHÓM B — Bạn cấu hình trong SecurityConfig
┌────────────────────────────────────────────────────────────────┐
│ SecurityFilterChain                                            │
│ • cấu hình phân quyền                                          │
│ • bật OAuth2/OIDC Login                                        │
│ • tùy biến Authorization Request                               │
│   (thêm access_type=offline + prompt=consent)                  │
│ • cấu hình Login / Logout                                      │
└────────────────────────────────────────────────────────────────┘
                         │
                         ▼

NHÓM C — Spring Security tự tạo và tự vận hành
┌────────────────────────────────────────────────────────────────┐
│ • Endpoint                                                     │
│     /oauth2/authorization/google                               │
│     /login/oauth2/code/google                                  │
│                                                                │
│ • Filter                                                       │
│     OAuth2AuthorizationRequestRedirectFilter                   │
│     OAuth2LoginAuthenticationFilter                            │
│                                                                │
│ • OAuth2AuthorizedClientRepository                             │
│     (lưu OAuth2AuthorizedClient theo Session)                  │
│                                                                │
│ • OidcUserService                                              │
│     (tạo OidcUser sau khi xác thực ID Token)                   │
│                                                                │
│ • OAuth2AuthorizedClientArgumentResolver                       │
│     (phục vụ @RegisteredOAuth2AuthorizedClient)                │
└────────────────────────────────────────────────────────────────┘
```

>**Lưu ý:** Trong project này, lập trình viên chỉ cần cấu hình `application.properties` và `SecurityFilterChain`. Các endpoint, filter, quá trình tạo Authorization Request, đổi Authorization Code lấy Token, xác thực ID Token và quản lý `OAuth2AuthorizedClient` đều được Spring Security tự động tạo và phối hợp thực hiện.

**Cách các nhóm phối hợp** — vòng đời một request, đi **một chiều từ trên xuống**:

```
(1) Browser truy cập /profile
        │
        ▼
(2) Spring Security phát hiện endpoint yêu cầu xác thực
        │
        ▼
(3) OAuth2AuthorizationRequestRedirectFilter
        │
        ├─ tạo Authorization Request
        │     • state
        │     • nonce
        │     • PKCE
        │     • access_type=offline
        │     • prompt=consent
        │
        └─ 302 Redirect sang Google
        │
        ▼
(4) Người dùng đăng nhập Google và đồng ý cấp quyền
        │
        ▼
(5) Google redirect về
    /login/oauth2/code/google?code=...&state=...
        │
        ▼
(6) OAuth2LoginAuthenticationFilter
        │
        ├─ kiểm tra state
        ├─ đổi Authorization Code lấy Token
        ├─ xác thực ID Token
        ├─ tạo OidcUser
        ├─ lưu SecurityContext
        └─ lưu OAuth2AuthorizedClient
        │
        ▼
(7) Redirect tới /profile
        │
        ▼
(8) Controller thực thi
        │
        └─ nhận OidcUser từ SecurityContext
           và render giao diện
```

> **Ghi nhớ:** Từ lúc request đi vào `SecurityFilterChain` cho đến khi `OidcUser` được tạo và lưu vào `SecurityContext`, hầu hết công việc đều do Spring Security tự động thực hiện. Trong dự án này, lập trình viên chỉ cấu hình **OAuth2 Client** và **SecurityFilterChain**; còn việc tạo Authorization Request, đổi Authorization Code lấy Token, xác thực ID Token và quản lý `OAuth2AuthorizedClient` đều là cơ chế sẵn có của framework.

## 2. TẦNG 1 — Các thành phần HIỆN trong `SecurityConfig`

### 2.1. `SecurityFilterChain` + `permitAll()`

> **Khái niệm:** `SecurityFilterChain` là **chuỗi các Servlet Filter của Spring Security** mà mọi HTTP request đều phải đi qua trước khi tới Controller. Đây là thành phần trung tâm chịu trách nhiệm thực thi toàn bộ cơ chế bảo mật của ứng dụng.
>
> Trong Spring Boot 3.x / Spring Security 6+, lập trình viên khai báo `SecurityFilterChain` dưới dạng một `@Bean` và cấu hình thông qua đối tượng `HttpSecurity`. Khi ứng dụng khởi động, Spring Security sẽ đọc các cấu hình này để xây dựng chuỗi Filter tương ứng.

> `permitAll()` là một **quy tắc phân quyền** (authorization rule), chịu trách nhiệm cho phép **mọi request truy cập mà không cần authentication**.

```java
@Bean
public SecurityFilterChain filterChain(HttpSecurity http,
        ClientRegistrationRepository clientRegistrationRepository) throws Exception {

    http
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/", "/error").permitAll()
            .anyRequest().authenticated()
        )
        .oauth2Login(oauth2 -> oauth2
            .defaultSuccessUrl("/profile", true)
            .authorizationEndpoint(authz -> authz
                .authorizationRequestResolver(
                    offlineAccessResolver(clientRegistrationRepository)
                )
            )
        )
        .logout(logout -> logout
            .logoutSuccessUrl("/")
        );

    return http.build();
}
```
`SecurityFilterChain` có thể xem như **"bộ luật bảo mật"** của toàn bộ ứng dụng. Mọi HTTP request trước khi tới Controller đều phải đi qua chuỗi Filter này.

Trong dự án, `SecurityFilterChain` thực hiện bốn nhiệm vụ chính:

- **Cấu hình phân quyền truy cập** thông qua `authorizeHttpRequests()`.
- **Kích hoạt cơ chế OpenID Connect Login** thông qua `oauth2Login()`.
- **Tùy biến Authorization Request** trước khi chuyển hướng người dùng sang Google.
- **Cấu hình Logout** sau khi người dùng đăng xuất.

Ngoài ra, tham số:

```java
ClientRegistrationRepository clientRegistrationRepository
```

được **Spring Boot tự động inject** vào phương thức `filterChain()`. Thành phần này chứa toàn bộ thông tin cấu hình của OAuth2 Client (Google) được tạo từ `application.properties` và sẽ được sử dụng ở phần `offlineAccessResolver()` để xây dựng Authorization Request.

### 2.2. `oauth2Login()`

> **Khái niệm:** `oauth2Login()` là một **DSL (Domain Specific Language)** trên `HttpSecurity`, dùng để **kích hoạt cơ chế OAuth2 Login / OpenID Connect (OIDC) Login** của Spring Security.
>
> Sau khi được cấu hình, Spring Security sẽ tự động tạo và phối hợp các thành phần cần thiết để thực hiện **Authorization Code Flow kết hợp OpenID Connect**, bao gồm:
>
> - tạo Authorization Request;
> - sinh `state` để chống CSRF;
> - sinh `nonce` để chống ID Token Replay Attack;
> - sinh PKCE (`code_verifier`, `code_challenge`);
> - chuyển hướng người dùng sang Google;
> - nhận Authorization Code sau khi người dùng xác thực;
> - đổi Authorization Code lấy Access Token, Refresh Token và ID Token;
> - xác thực chữ ký và các claim của ID Token;
> - tạo `OidcUser` và lưu thông tin xác thực vào `SecurityContext`.

Trong dự án, `oauth2Login()` được cấu hình như sau:

```java
.oauth2Login(oauth2 -> oauth2
        .defaultSuccessUrl("/profile", true)
        .authorizationEndpoint(authz -> authz
                .authorizationRequestResolver(
                        offlineAccessResolver(clientRegistrationRepository)
                )
        )
)
```

`oauth2Login()` đóng vai trò là **điểm khởi động toàn bộ cơ chế đăng nhập bằng OpenID Connect** của ứng dụng. Khi người dùng truy cập một URL yêu cầu xác thực (ví dụ `/profile`) nhưng chưa đăng nhập, Spring Security sẽ tự động khởi động quá trình đăng nhập với Google.

Trong cấu hình trên:

- `defaultSuccessUrl("/profile", true)` quy định sau khi đăng nhập thành công, người dùng luôn được chuyển hướng đến `/profile`.
- `authorizationEndpoint(...)` cho phép tùy biến **Authorization Request** trước khi chuyển hướng người dùng sang Google.
- `authorizationRequestResolver(...)` thay thế `DefaultOAuth2AuthorizationRequestResolver` bằng `offlineAccessResolver()` để bổ sung các tham số riêng của Google (`access_type=offline` và `prompt=consent`), nhằm yêu cầu Google cấp thêm **Refresh Token**.

> ⚠️ **Lưu ý:** `oauth2Login()` không phải là nơi trực tiếp tạo Authorization Request hay đổi Authorization Code lấy Token. Nó chỉ **kích hoạt và cấu hình** cơ chế OAuth2/OIDC Login; toàn bộ quá trình xử lý sẽ được các Filter và AuthenticationProvider của Spring Security tự động thực hiện ở phía sau.

### 2.3. `authorizationRequestResolver` — vì sao cần tùy biến?

> **Khái niệm:** `OAuth2AuthorizationRequestResolver` là thành phần chịu trách nhiệm **tạo `OAuth2AuthorizationRequest`** mỗi khi người dùng bắt đầu quá trình đăng nhập bằng OAuth2/OIDC.
>
> `OAuth2AuthorizationRequest` chứa toàn bộ thông tin sẽ được gửi tới Authorization Server, bao gồm:
>
> - `client_id`
> - `redirect_uri`
> - `scope`
> - `response_type`
> - `state`
> - các tham số mở rộng (nếu có)
>
> Spring Security đã cung cấp sẵn `DefaultOAuth2AuthorizationRequestResolver` để tạo Authorization Request theo chuẩn OAuth2/OpenID Connect. Trong dự án này, ta **không thay thế hoàn toàn** resolver mặc định, mà chỉ **tùy biến** nó để bổ sung thêm một số tham số riêng của Google.

Trong dự án, resolver được cấu hình như sau:

```java
private OAuth2AuthorizationRequestResolver offlineAccessResolver(
        ClientRegistrationRepository repo) {

    DefaultOAuth2AuthorizationRequestResolver resolver =
            new DefaultOAuth2AuthorizationRequestResolver(
                    repo, "/oauth2/authorization");

    resolver.setAuthorizationRequestCustomizer(customizer ->
            customizer.additionalParameters(params -> {
                params.put("access_type", "offline");
                params.put("prompt", "consent");
            }));

    return resolver;
}
```

### Giải thích từng phần

#### `DefaultOAuth2AuthorizationRequestResolver`

```java
new DefaultOAuth2AuthorizationRequestResolver(
        repo,
        "/oauth2/authorization")
```

Khởi tạo `DefaultOAuth2AuthorizationRequestResolver` và khai báo rằng mọi request có dạng:

```
/oauth2/authorization/{registrationId}
```

sẽ được resolver này xử lý.

Ví dụ, khi người dùng truy cập:

```
/oauth2/authorization/google
```

Spring Security sẽ:

1. lấy `ClientRegistration` có `registrationId = "google"` từ `ClientRegistrationRepository`;
2. tạo `OAuth2AuthorizationRequest`;
3. bổ sung các tham số chuẩn của OAuth2/OIDC như `client_id`, `redirect_uri`, `scope`, `response_type`, `state`,...
4. tự động sinh `nonce` và PKCE (`code_verifier`, `code_challenge`) khi cần;
5. chuyển `OAuth2AuthorizationRequest` cho `OAuth2AuthorizationRequestRedirectFilter` để redirect trình duyệt sang Google.

---

#### `setAuthorizationRequestCustomizer(...)`

```java
resolver.setAuthorizationRequestCustomizer(...)
```

Phương thức này cho phép **can thiệp vào Authorization Request trước khi nó được gửi tới Google**.

Trong dự án, ta chỉ bổ sung thêm hai tham số:

```java
params.put("access_type", "offline");
params.put("prompt", "consent");
```

Đây là hai tham số mở rộng do Google cung cấp (không thuộc chuẩn OAuth2 hay OpenID Connect).

- `access_type=offline`
  - yêu cầu Google cấp thêm **Refresh Token** cùng với Access Token.

- `prompt=consent`
  - buộc Google luôn hiển thị màn hình xin quyền (Consent Screen), từ đó cấp lại Refresh Token ngay cả khi người dùng đã từng cấp quyền cho ứng dụng trước đó.

Nhờ đó, sau khi Authorization Code Flow hoàn tất, `OAuth2AuthorizedClient` sẽ chứa cả **Access Token** và **Refresh Token**, cho phép Spring Security tự động làm mới Access Token khi nó hết hạn.

> ⚠️ **Lưu ý:** Trong dự án này, `authorizationRequestResolver` **không tự sinh PKCE, `state` hay `nonce`**. Các giá trị này vẫn được Spring Security tự động tạo trong quá trình xây dựng `OAuth2AuthorizationRequest`. Resolver chỉ có nhiệm vụ bổ sung thêm các tham số đặc thù của Google trước khi request được gửi tới Authorization Server.

### 2.4. `OAuth2AuthorizedClientManager` — tự động quản lý Access Token

> ⚠️ **Lưu ý về vị trí:** thành phần này **không** xuất hiện trong `SecurityConfig`; nó do **Spring Boot auto-config** tạo sẵn (dự án không khai bean nào). Mục này đặt ở đây vì nó là "mảnh ghép" khiến `@RegisteredOAuth2AuthorizedClient` ở controller hoạt động (chi tiết luồng xem mục 3.4 và 5.2).

> **Trước hết, cần hiểu `OAuth2AuthorizedClient` là gì.**

`OAuth2AuthorizedClient` là object đại diện cho **một OAuth2 Client đã được người dùng cấp quyền (authorized)**. Nó chứa toàn bộ thông tin cần thiết để ứng dụng **tiếp tục gọi Resource Server thay mặt người dùng**, bao gồm:

- `ClientRegistration` (thông tin ứng dụng đã đăng ký với Authorization Server) - Xem phần 3.1
- `AccessToken`
- `RefreshToken` (nếu được cấp)

Có thể hình dung như sau:

```
OAuth2AuthorizedClient
│
├── ClientRegistration
├── AccessToken
└── RefreshToken
```

Sau khi người dùng hoàn thành **Authorization Code Flow**, Spring sẽ tạo một `OAuth2AuthorizedClient` và lưu lại để các request sau có thể tái sử dụng **Access Token** hoặc **Refresh Token**, thay vì phải bắt người dùng đăng nhập và cấp quyền với Google từ đầu.

Mặc định, khi sử dụng `oauth2Login()`, Spring Boot sẽ tự cấu hình một **`AuthenticatedPrincipalOAuth2AuthorizedClientRepository`**.

Đây là implementation mặc định của `OAuth2AuthorizedClientRepository`, chịu trách nhiệm **lưu và đọc `OAuth2AuthorizedClient`**.

Tuy nhiên, Repository này **không trực tiếp lưu dữ liệu**, mà chỉ đóng vai trò **điều phối (delegate)**. Khi cần lưu hoặc đọc `OAuth2AuthorizedClient`, nó sẽ quyết định sử dụng cơ chế nào dựa trên trạng thái xác thực của request hiện tại.

Có hai trường hợp:

- **Request đã được xác thực** (đã có `Authentication` trong `SecurityContext`)

  Repository sẽ ủy quyền cho **`OAuth2AuthorizedClientService`** (mặc định là `InMemoryOAuth2AuthorizedClientService`) để lưu và tra cứu `OAuth2AuthorizedClient`.

- **Request là anonymous** (chưa có `Authentication`)

  Repository sẽ ủy quyền cho **`HttpSessionOAuth2AuthorizedClientRepository`**, lưu `OAuth2AuthorizedClient` trong `HttpSession` của người dùng.

Trong dự án này, ứng dụng sử dụng **OIDC Login** thông qua `oauth2Login()`.

Sau khi người dùng đăng nhập Google thành công, Spring sẽ:

- tạo một `OidcAuthenticationToken`;
- trong `OidcAuthenticationToken`, **principal** là một `OidcUser` (đại diện cho danh tính của người dùng);
- đặt `Authentication` này vào `SecurityContext`;
- đồng thời lưu `SecurityContext` vào `HttpSession` để duy trì trạng thái đăng nhập giữa các request.

Nhờ vậy, ở các request tiếp theo, Spring luôn khôi phục được `Authentication` từ `HttpSession`. Do đó, `AuthenticatedPrincipalOAuth2AuthorizedClientRepository` sẽ **không sử dụng `HttpSessionOAuth2AuthorizedClientRepository`**, mà sẽ ủy quyền cho **`InMemoryOAuth2AuthorizedClientService`**.

Có thể hình dung như sau:

```
AuthenticatedPrincipalOAuth2AuthorizedClientRepository
                    │
        Có Authentication ?
             │
      ┌──────┴──────────────────────────────────────┐
      │                                             │
     Có                                           Không
      │                                             │
      ▼                                             ▼
OAuth2AuthorizedClientService   HttpSessionOAuth2AuthorizedClientRepository
      (InMemory)
```

Trong project này, luồng thực tế luôn đi theo **nhánh bên trái**, vì sau khi đăng nhập thành công người dùng đã có `Authentication`.

`InMemoryOAuth2AuthorizedClientService` sẽ lưu `OAuth2AuthorizedClient` theo hai khóa:

- `registrationId` (ví dụ: `"google"`);
- `principalName`.

Ở đây cần phân biệt:

- **principal** là object `OidcUser`;
- **principalName** là giá trị trả về từ `Authentication#getName()`. Với `OidcUser`, giá trị này mặc định chính là claim **`sub`** (Subject Identifier) trong ID Token.

Có thể hình dung như sau:

```
OidcAuthenticationToken
        │
        ▼
     principal
        │
        ▼
      OidcUser
        │
        ├── sub
        ├── email
        ├── name
        └── ...
        │
        ▼
Authentication#getName()
        │
        ▼
principalName = sub
        │
        ▼
InMemoryOAuth2AuthorizedClientService
│
├── ("google", "110...A")
│      │
│      ▼
│   OAuth2AuthorizedClient
│
└── ("google", "220...B")
       │
       ▼
    OAuth2AuthorizedClient
```

Vì khóa lưu là **principal name** (không phải `JSESSIONID`):

- Hai **tài khoản Google khác nhau** → hai `OAuth2AuthorizedClient` riêng, không ảnh hưởng nhau.
- **Cùng một tài khoản** đăng nhập trên hai trình duyệt → **dùng chung** một `OAuth2AuthorizedClient` (cùng principal); token được chia sẻ, lần refresh này ghi đè lần kia.

> 💡 **Phân biệt hai thứ hay bị nhầm:**
> - **Trạng thái đăng nhập** (`SecurityContext` / `Authentication`) được lưu trong **`HttpSession`** → đây là lý do người dùng "vẫn đang đăng nhập" giữa các request.
> - **Token** (`OAuth2AuthorizedClient`) lại được lưu trong **`OAuth2AuthorizedClientService`** (InMemory, theo principal), **tách biệt** với session.
>
> `InMemoryOAuth2AuthorizedClientService` giữ token trong **bộ nhớ tiến trình** → mất khi ứng dụng khởi động lại. Muốn bền vững (DB) thì thay bằng `JdbcOAuth2AuthorizedClientService`.

---

> **`OAuth2AuthorizedClientManager` là gì?**

`OAuth2AuthorizedClientManager` là **thành phần điều phối trung tâm** chịu trách nhiệm đảm bảo ứng dụng luôn có một `OAuth2AuthorizedClient` hợp lệ để sử dụng.

Trong dự án này, **Controller không trực tiếp làm việc với `OAuth2AuthorizedClientManager`**.

Thay vào đó, khi Spring MVC chuẩn bị gọi một method của Controller và gặp tham số được đánh dấu bằng `@RegisteredOAuth2AuthorizedClient`, **`OAuth2AuthorizedClientArgumentResolver`** sẽ được kích hoạt để tạo giá trị cho tham số này.

Để lấy được một `OAuth2AuthorizedClient` hợp lệ, `OAuth2AuthorizedClientArgumentResolver` sẽ **ủy quyền** cho `OAuth2AuthorizedClientManager`.

Có thể hình dung luồng như sau:

```
Controller
      │
      ▼
@RegisteredOAuth2AuthorizedClient
      │
      ▼
OAuth2AuthorizedClientArgumentResolver
      │
      ▼
OAuth2AuthorizedClientManager
```

Sau khi nhận được yêu cầu, `OAuth2AuthorizedClientManager` sẽ thực hiện các bước sau:

- Kiểm tra xem người dùng hiện tại đã có `OAuth2AuthorizedClient` hay chưa.
- Nếu đã có và Access Token vẫn còn hiệu lực, trả về ngay.
- Nếu Access Token đã hết hạn nhưng vẫn còn Refresh Token, sử dụng Refresh Token để lấy Access Token mới.
- Nếu chưa có `OAuth2AuthorizedClient`, lựa chọn `AuthorizationCodeOAuth2AuthorizedClientProvider` để khởi động lại Authorization Code Flow.

Nói cách khác, `OAuth2AuthorizedClientManager` **không trực tiếp thực hiện việc lấy hay refresh Access Token**, mà chỉ đóng vai trò **điều phối**. Việc thực thi sẽ được **ủy quyền** cho các `OAuth2AuthorizedClientProvider`, trong đó mỗi Provider chỉ phụ trách **một cơ chế cấp hoặc làm mới Access Token**.

Các Provider phổ biến gồm:

- **`AuthorizationCodeOAuth2AuthorizedClientProvider`**

  Chịu trách nhiệm xử lý **Authorization Code Grant**. Nếu người dùng chưa có `OAuth2AuthorizedClient`, Provider sẽ ném `ClientAuthorizationRequiredException`. Exception này sau đó được `OAuth2AuthorizationRequestRedirectFilter` bắt để chuyển hướng người dùng sang Authorization Server bắt đầu Authorization Code Flow. Sau khi người dùng cấp quyền, việc trao đổi Authorization Code lấy Access Token sẽ do `OAuth2AuthorizationCodeGrantFilter` thực hiện.

- **`RefreshTokenOAuth2AuthorizedClientProvider`**

  Chịu trách nhiệm xử lý **Refresh Token Grant**. Khi Access Token đã hết hạn nhưng vẫn còn Refresh Token, Provider sẽ sử dụng Refresh Token để lấy Access Token mới mà không yêu cầu người dùng đăng nhập hoặc cấp quyền lại.

- **`ClientCredentialsOAuth2AuthorizedClientProvider`**

  Chịu trách nhiệm xử lý **Client Credentials Grant**, dùng trong trường hợp ứng dụng tự xác thực để lấy Access Token mà không có người dùng tham gia.

- ...

Có thể hình dung mối quan hệ giữa `OAuth2AuthorizedClientManager` và các Provider như sau:

```
OAuth2AuthorizedClientArgumentResolver
                 │
                 ▼
OAuth2AuthorizedClientManager
                 │
                 ▼
      Có OAuth2AuthorizedClient ?
                 │
      ┌──────────┴──────────┐
      │                     │
     Có                   Chưa có
      │                     │
      ▼                     ▼
Access Token           AuthorizationCode
còn hạn ?              OAuth2AuthorizedClientProvider
      │                     │
 ┌────┴────┐                │
 │         │                ▼
Có       Không      ClientAuthorizationRequiredException
 │         │                │
 ▼         ▼                ▼
Trả về   RefreshToken   Authorization Code Flow
ngay      Provider
 │         │
 └────┬────┘
      ▼
OAuth2AuthorizedClient
```

Sơ đồ trên có thể hiểu theo thứ tự như sau:

1. `OAuth2AuthorizedClientArgumentResolver` yêu cầu `OAuth2AuthorizedClientManager` cung cấp một `OAuth2AuthorizedClient`.
2. Manager kiểm tra xem người dùng hiện tại đã có `OAuth2AuthorizedClient` hay chưa.
3. Nếu đã có, Manager tiếp tục kiểm tra Access Token:
   - Nếu Access Token còn hiệu lực, trả về ngay.
   - Nếu Access Token đã hết hạn nhưng có Refresh Token, sử dụng `RefreshTokenOAuth2AuthorizedClientProvider` để lấy Access Token mới rồi trả về.
4. Nếu chưa có `OAuth2AuthorizedClient`, Manager sử dụng `AuthorizationCodeOAuth2AuthorizedClientProvider` để khởi động Authorization Code Flow.
5. Sau khi có được một `OAuth2AuthorizedClient` hợp lệ, Manager trả object này về cho `OAuth2AuthorizedClientArgumentResolver`, và Resolver truyền nó vào tham số của method Controller.

## 3. TẦNG 2 — Các thành phần Spring Boot tự động tạo (Auto Configuration)

Đây là những thành phần **không xuất hiện trong `SecurityConfig`**, nhưng được Spring Boot tự động khởi tạo dựa trên các dependency và file cấu hình. Chính các thành phần này phối hợp với `SecurityFilterChain` để hoàn thành toàn bộ quá trình đăng nhập bằng OpenID Connect.

### 3.1. `ClientRegistrationRepository` — được tạo từ `application.properties`

> **Khái niệm:** `ClientRegistration` là object mô tả **cấu hình của một OAuth2/OpenID Connect Client** (ví dụ Google, GitHub, Microsoft...). Nó chứa toàn bộ thông tin cần thiết để ứng dụng giao tiếp với Authorization Server, như:
>
> - `client-id`
> - `client-secret`
> - `scope`
> - `redirect-uri`
> - các endpoint của Authorization Server (`authorization-uri`, `token-uri`, `jwk-set-uri`, `issuer-uri`, ...)
>
> `ClientRegistrationRepository` là **kho lưu trữ các `ClientRegistration`**, cho phép Spring Security tra cứu cấu hình theo `registrationId` (ví dụ `"google"`). Mặc định, Spring Boot sử dụng `InMemoryClientRegistrationRepository`.

Trong dự án, ta **không tự tạo** `ClientRegistrationRepository`. Thay vào đó, Spring Boot sẽ đọc các cấu hình trong `application.properties`:

```properties
spring.security.oauth2.client.registration.google.client-id=${GOOGLE_CLIENT_ID}
spring.security.oauth2.client.registration.google.client-secret=${GOOGLE_CLIENT_SECRET}
spring.security.oauth2.client.registration.google.scope=openid,profile,email,https://www.googleapis.com/auth/calendar.readonly
```

Sau đó tự động tạo một `ClientRegistration` có `registrationId = "google"` và lưu vào `ClientRegistrationRepository`.

Đối với Google, ta chỉ cần khai báo `client-id`, `client-secret` và `scope`. Các thông tin như:

- `authorization-uri`
- `token-uri`
- `jwk-set-uri`
- `issuer-uri`

không cần khai báo thủ công vì Spring Boot đã tự động bổ sung thông qua `CommonOAuth2Provider.GOOGLE`.

Có thể hình dung như sau:

```text
application.properties
        │
        ▼
ClientRegistration
(registrationId = "google")
        │
        ▼
InMemoryClientRegistrationRepository
```

Khi cần bắt đầu quá trình đăng nhập, `OAuth2AuthorizationRequestResolver` sẽ lấy `ClientRegistration` từ `ClientRegistrationRepository` để xây dựng `OAuth2AuthorizationRequest`. Sau đó, các Filter và các thành phần khác của Spring Security cũng sẽ tiếp tục sử dụng `ClientRegistration` này trong suốt Authorization Code Flow.

> 💡 **Lưu ý:** Dự án sử dụng các scope `openid`, `profile` và `email`, vì đây là một ứng dụng **OpenID Connect Login**. Scope `openid` cho phép Google trả về **ID Token**, còn `profile` và `email` cho phép Spring Security xây dựng `OidcUser` chứa thông tin người dùng sau khi đăng nhập thành công. Ngoài ra, scope `https://www.googleapis.com/auth/calendar.readonly` được sử dụng để ứng dụng có thể gọi Google Calendar API thay mặt người dùng.

### 3.2. Hai Endpoint tự sinh (không có Controller nào cho chúng)

> **Khái niệm:** Khi cấu hình `oauth2Login()`, Spring Security sẽ **tự động đăng ký hai endpoint** phục vụ quá trình đăng nhập bằng OAuth2/OpenID Connect. Hai endpoint này **không được định nghĩa bằng `@Controller` hay `@GetMapping`**, mà được các Servlet Filter trong `SecurityFilterChain` tự động xử lý.

| Endpoint | Thành phần xử lý | Nhiệm vụ |
|----------|------------------|----------|
| `/oauth2/authorization/{registrationId}` | `OAuth2AuthorizationRequestRedirectFilter` | Khởi động Authorization Code Flow, tạo Authorization Request và chuyển hướng người dùng sang Google. |
| `/login/oauth2/code/{registrationId}` | `OAuth2LoginAuthenticationFilter` | Nhận callback từ Google, đổi Authorization Code lấy Token, xác thực ID Token và hoàn tất quá trình đăng nhập. |

Trong dự án, `registrationId` là:

```
google
```

nên hai endpoint thực tế là:

```
/oauth2/authorization/google
/login/oauth2/code/google
```

> 💡 **Lưu ý:** Nếu tìm trong project sẽ **không thấy** bất kỳ `@GetMapping("/oauth2/authorization/google")` hay `@GetMapping("/login/oauth2/code/google")` nào. Đây là các endpoint do Spring Security tự đăng ký khi `oauth2Login()` được kích hoạt.

Ngoài ra, endpoint callback:

```
/login/oauth2/code/google
```

phải trùng với **Authorized Redirect URI** đã khai báo trên Google Cloud Console. Sau khi người dùng đăng nhập và cấp quyền, Google sẽ redirect trình duyệt quay trở lại đúng endpoint này để Spring Security tiếp tục xử lý.

---

### 3.3. Hai Filter cốt lõi của OpenID Connect Login

> **Khái niệm:** Hai endpoint ở mục trên không được xử lý bởi Controller mà bởi **hai Servlet Filter** nằm trong `SecurityFilterChain`. Đây chính là "phần chìm" của Spring Security, chịu trách nhiệm thực hiện gần như toàn bộ Authorization Code Flow kết hợp OpenID Connect.

---

#### a. `OAuth2AuthorizationRequestRedirectFilter` — Khởi động Authorization Code Flow

`OAuth2AuthorizationRequestRedirectFilter` là **Servlet Filter** chịu trách nhiệm **khởi động Authorization Code Flow**.

Filter này được kích hoạt khi trình duyệt truy cập endpoint:

```
GET /oauth2/authorization/google
```

hoặc khi `OAuth2AuthorizedClientManager` phát hiện **chưa có `OAuth2AuthorizedClient`** và `AuthorizationCodeOAuth2AuthorizedClientProvider` ném ra `ClientAuthorizationRequiredException`.

Sau khi được kích hoạt, Filter sẽ thực hiện các bước sau:

##### 1. Tạo `OAuth2AuthorizationRequest`

Filter gọi `OAuth2AuthorizationRequestResolver` (được cấu hình trong mục **2.3**) để tạo một `OAuth2AuthorizationRequest`.

Trước tiên, `DefaultOAuth2AuthorizationRequestResolver` xây dựng các tham số chuẩn của Authorization Request dựa trên `ClientRegistration`, bao gồm:

- `client_id`
- `redirect_uri`
- `response_type=code`
- `scope`
- `state`

Nếu ứng dụng sử dụng **OpenID Connect** (scope có `openid`), Spring sẽ tự động bổ sung thêm:

- `nonce`

Trong dự án này, Resolver được tùy biến bằng `offlineAccessResolver()`, vì vậy trong quá trình xây dựng request, Spring còn bổ sung thêm:

```java
private OAuth2AuthorizationRequestResolver offlineAccessResolver(ClientRegistrationRepository repo) {
    DefaultOAuth2AuthorizationRequestResolver resolver =
            new DefaultOAuth2AuthorizationRequestResolver(repo, AUTHORIZATION_BASE_URI);
    resolver.setAuthorizationRequestCustomizer(customizer ->
            customizer.additionalParameters(params -> {
                params.put("access_type", "offline");
                params.put("prompt", "consent");
            }));
    return resolver;
}
```

- PKCE
    - sinh `code_verifier`
    - tính `code_challenge`
    - thêm `code_challenge_method=S256`
- tham số riêng của Google:
    - `access_type=offline`
    - `prompt=consent`

> **Lưu ý:** chỉ có `code_challenge` được gửi sang Google. `code_verifier` **không được gửi**, mà được lưu lại để sử dụng ở bước đổi Authorization Code lấy Access Token.

##### 2. Lưu `OAuth2AuthorizationRequest`

Sau khi `OAuth2AuthorizationRequest` được tạo xong, Filter sẽ lưu object này vào `AuthorizationRequestRepository`.

Mặc định Spring Security sử dụng:

```
HttpSessionOAuth2AuthorizationRequestRepository
```

Repository này không có nơi lưu trữ riêng mà chỉ sử dụng `HttpSession` của người dùng.

Có thể hình dung như sau:

```
Browser
    │
Cookie: JSESSIONID
    │
    ▼
HttpSession
    │
    └── SPRING_SECURITY_SAVED_AUTHORIZATION_REQUEST
            │
            ▼
    OAuth2AuthorizationRequest
        ├── state
        ├── redirect_uri
        ├── code_verifier
        ├── client_id
        ├── scope
        └── ...
```

Việc lưu lại `OAuth2AuthorizationRequest` giúp Spring Security có thể:

- đối chiếu `state` khi Google callback để chống CSRF;
- lấy lại `code_verifier` nhằm hoàn tất cơ chế PKCE;
- biết chính xác Authorization Request ban đầu để tiếp tục Authorization Code Flow.

---

##### 3. Redirect sang Authorization Server

Cuối cùng, Filter trả về HTTP **302 Redirect**, chuyển trình duyệt sang Authorization Server (Google).

Toàn bộ quá trình có thể hình dung như sau:

```
Browser
    │
GET /oauth2/authorization/google
    │
    ▼
OAuth2AuthorizationRequestRedirectFilter
    │
    ▼
OAuth2AuthorizationRequestResolver
    │
    ▼
OAuth2AuthorizationRequest
    │
    ▼
HttpSessionOAuth2AuthorizationRequestRepository
    │
    ▼
HttpSession
    │
    ▼
302 Redirect
    │
    ▼
Google Authorization Server
```

> Có thể thấy `OAuth2AuthorizationRequestRedirectFilter` **không trực tiếp xây dựng Authorization Request**, cũng **không tự sinh PKCE hay nonce**. Vai trò của Filter là **điều phối**: gọi `OAuth2AuthorizationRequestResolver` để tạo `OAuth2AuthorizationRequest`, lưu request vào `AuthorizationRequestRepository`, sau đó redirect trình duyệt sang Authorization Server để bắt đầu Authorization Code Flow.

---

#### **b) `OAuth2LoginAuthenticationFilter` — Hoàn tất OpenID Connect Login**

Sau khi người dùng đăng nhập thành công và đồng ý cấp quyền trên Google, Authorization Server sẽ redirect trình duyệt quay trở lại ứng dụng:

```
GET /login/oauth2/code/google?code=...&state=...
```

Lúc này, `OAuth2LoginAuthenticationFilter` sẽ tiếp tục hoàn tất quá trình xác thực và thiết lập trạng thái đăng nhập cho người dùng.

Filter thực hiện lần lượt các bước sau:

##### 1. Lấy lại `OAuth2AuthorizationRequest`

Filter lấy `OAuth2AuthorizationRequest` đã được lưu trước đó trong `AuthorizationRequestRepository` (mặc định là `HttpSessionOAuth2AuthorizationRequestRepository`).

Từ object này, Spring Security lấy lại các thông tin cần thiết như:

- `state`
- `redirect_uri`
- `code_verifier` (PKCE)
- các tham số của Authorization Request ban đầu.

---

##### 2. Kiểm tra `state`

Spring Security đối chiếu giá trị `state` trong callback với `state` đã lưu trong `OAuth2AuthorizationRequest`.

Nếu hai giá trị không khớp, request sẽ bị từ chối nhằm chống tấn công **CSRF**.

---

##### 3. Đổi Authorization Code lấy Token

Sau khi `state` hợp lệ, Spring Security sử dụng Authorization Code để gọi **Token Endpoint** của Google.

Request này bao gồm:

- Authorization Code
- `client_id`
- `client_secret`
- `redirect_uri`
- `code_verifier` (PKCE)

Nếu thành công, Google trả về:

- Access Token
- Refresh Token (nếu được cấp)
- ID Token

---

##### 4. Xác thực ID Token

Spring Security sử dụng `OidcIdTokenDecoderFactory` để xác thực ID Token.

Quá trình này bao gồm:

- kiểm tra chữ ký số thông qua JWKS của Google;
- kiểm tra các claim quan trọng như:
    - `iss`
    - `aud`
    - `exp`
    - `nonce`
    - ...

Nếu ID Token không hợp lệ, quá trình đăng nhập sẽ thất bại.

---

##### 5. Tạo `OidcUser`

Sau khi ID Token được xác thực thành công, Spring Security gọi `OidcUserService` để tạo một `OidcUser`.

`OidcUser` đại diện cho người dùng đã đăng nhập và chứa các thông tin định danh như:

- Subject (`sub`)
- Họ tên (`name`)
- Email (`email`)
- Ảnh đại diện (`picture`)
- các claim khác trong ID Token và UserInfo Endpoint (nếu có).

---

##### 6. Tạo `OAuth2AuthorizedClient`

Spring Security đóng gói:

- `ClientRegistration`
- Access Token
- Refresh Token

thành một `OAuth2AuthorizedClient`, sau đó lưu thông qua `OAuth2AuthorizedClientRepository`.

Trong dự án này, do người dùng đã được xác thực thành công, `AuthenticatedPrincipalOAuth2AuthorizedClientRepository` sẽ ủy quyền cho `OAuth2AuthorizedClientService` (mặc định là `InMemoryOAuth2AuthorizedClientService`) để lưu `OAuth2AuthorizedClient` theo `principal`.

---

##### 7. Tạo `Authentication`

Tiếp theo, Spring Security tạo một `OidcAuthenticationToken`, trong đó:

- `principal` là `OidcUser`;
- `authorities` được lấy từ thông tin người dùng;
- `authorizedClientRegistrationId` là `"google"`.

`Authentication` này được đặt vào `SecurityContextHolder`.

Cuối request, `SecurityContext` sẽ được `SecurityContextRepository` (mặc định là `HttpSessionSecurityContextRepository`) lưu vào `HttpSession`, giúp những request sau có thể khôi phục lại trạng thái đăng nhập.

---

##### 8. Gọi `AuthenticationSuccessHandler`

Sau khi hoàn tất quá trình xác thực, Spring Security gọi `AuthenticationSuccessHandler`.

Do dự án cấu hình:

```
.defaultSuccessUrl("/profile", true)
```

nên Spring Security trả về HTTP **302 Redirect**, chuyển trình duyệt tới:

```
/profile
```

Ở request mới tới `/profile`, trình duyệt chỉ gửi kèm `JSESSIONID`. Spring Security sẽ sử dụng `JSESSIONID` để khôi phục `SecurityContext` từ `HttpSession`, sau đó đặt lại vào `SecurityContextHolder` trước khi Controller được gọi.

Nhờ vậy, Controller có thể nhận trực tiếp:

```
@AuthenticationPrincipal OidcUser user
```

mà không cần tự đọc `HttpSession` hay tự xác thực lại người dùng.

---

Toàn bộ quá trình có thể hình dung như sau:

```
Google Authorization Server
          │
302 Redirect
          │
GET /login/oauth2/code/google?code=...&state=...
          │
          ▼
OAuth2LoginAuthenticationFilter
          │
          ├── Lấy AuthorizationRequest từ AuthorizationRequestRepository
          ├── Kiểm tra state
          ├── Đổi Authorization Code lấy Token
          ├── Xác thực ID Token
          ├── Tạo OidcUser
          ├── Tạo OAuth2AuthorizedClient
          ├── Tạo Authentication
          ├── Đặt vào SecurityContextHolder
          └── Lưu SecurityContext vào HttpSession
          │
          ▼
AuthenticationSuccessHandler
          │
          ▼
302 Redirect
          │
          ▼
GET /profile
          │
          ▼
SecurityContextHolderFilter
          │
          ▼
Khôi phục SecurityContext từ HttpSession
          │
          ▼
Controller (@AuthenticationPrincipal OidcUser)
```

#### **c) `Toàn bộ luồng từ đầu tới cuối`**

> **Giai đoạn 1. Request đầu tiên tới ứng dụng**

Lần đầu tiên người dùng truy cập ứng dụng, trình duyệt **chưa có `JSESSIONID`**, vì vậy Servlet Container sẽ tạo một `HttpSession` mới trước khi request đi vào `SecurityFilterChain`.

```
Browser
    │
    │ GET /profile
    ▼
Tomcat (Servlet Container)
    │
    ▼
Có JSESSIONID ?
    │
┌───┴────────────────────────┐
│                            │
Có                         Không
│                            │
▼                            ▼
Lấy HttpSession      Tạo HttpSession mới
│                            │
│                            ▼
│                    Sinh JSESSIONID
└────────────┬───────────────┘
             ▼
     SecurityFilterChain
             │
             ▼
     ... xử lý request ...
             │
             ▼
HTTP Response
Set-Cookie:
JSESSIONID=ABC123
             │
             ▼
Browser lưu Cookie
```


Giải thích

1. Browser gửi request đầu tiên tới ứng dụng.
2. Trước khi request đi vào Spring Security, **Servlet Container (Tomcat)** kiểm tra xem request có gửi cookie `JSESSIONID` hay không.
3. Nếu chưa có `JSESSIONID`, Tomcat sẽ:
    - tạo một `HttpSession` mới;
    - sinh một `JSESSIONID` duy nhất;
    - liên kết `JSESSIONID` với `HttpSession` vừa tạo.
4. Request tiếp tục đi vào `SecurityFilterChain` để Spring Security xử lý.
5. Khi response được trả về cho browser, Tomcat tự động thêm header:

```
Set-Cookie: JSESSIONID=ABC123; Path=/; HttpOnly
```

6. Browser lưu cookie này. Từ các request tiếp theo, browser sẽ tự động gửi:

```
Cookie: JSESSIONID=ABC123
```

để server có thể tìm lại đúng `HttpSession` của người dùng.

> **Lưu ý:** Việc tạo `HttpSession`, sinh `JSESSIONID`, thêm `Set-Cookie` vào response và ánh xạ `JSESSIONID → HttpSession` đều là trách nhiệm của **Servlet Container (Tomcat)**, không phải Spring Security. Spring Security chỉ tận dụng `HttpSession` này để lưu `SecurityContext`, `OAuth2AuthorizationRequest` và các thông tin cần thiết khác.

---

> **Giai đoạn 2. Khởi động Authorization Code Flow**

Do người dùng **chưa được xác thực**, `OAuth2AuthorizationRequestRedirectFilter` sẽ khởi động **Authorization Code Flow** bằng cách tạo `OAuth2AuthorizationRequest`, lưu request này vào `HttpSession`, sau đó chuyển hướng (redirect) trình duyệt sang Google.

```
SecurityFilterChain
        │
        ▼
OAuth2AuthorizationRequestRedirectFilter
        │
        ▼
OAuth2AuthorizationRequestResolver
        │
        ▼
OAuth2AuthorizationRequest
        │
        ├── client_id
        ├── redirect_uri
        ├── scope
        ├── state
        ├── nonce
        ├── code_challenge
        └── ...
        │
        ▼
HttpSessionOAuth2AuthorizationRequestRepository
        │
        ▼
HttpSession
        │
session.setAttribute(
    SPRING_SECURITY_SAVED_AUTHORIZATION_REQUEST,
    authorizationRequest
)
        │
        ▼
302 Redirect Response
(Location: Google Authorization Endpoint)
        │
        ▼
Tomcat
        │
        ├── Nếu HttpSession vừa được tạo
        │       ▼
        │  Set-Cookie:
        │  JSESSIONID=ABC123
        ▼
Browser
        │
        ├── Lưu JSESSIONID
        └── Redirect tới Google
                │
                ▼
Google Authorization Server
```

### Giải thích

1. `OAuth2AuthorizationRequestRedirectFilter` được kích hoạt khi người dùng truy cập endpoint:

   ```
   /oauth2/authorization/google
   ```

2. Filter gọi `OAuth2AuthorizationRequestResolver` để xây dựng một `OAuth2AuthorizationRequest`.

3. Trong project này, `DefaultOAuth2AuthorizationRequestResolver` được tùy biến thông qua `setAuthorizationRequestCustomizer(...)`, vì vậy trong quá trình tạo request, Spring sẽ bổ sung thêm:

    - PKCE
        - sinh `code_verifier`;
        - tính `code_challenge`;
        - thêm `code_challenge_method=S256`;
    - các tham số riêng của Google:
        - `access_type=offline`;
        - `prompt=consent`.

    > **Lưu ý:** Chỉ có `code_challenge` được gửi sang Google. `code_verifier` không được gửi mà sẽ được lưu lại để sử dụng khi đổi Authorization Code lấy Access Token.

4. Sau khi `OAuth2AuthorizationRequest` được tạo, `HttpSessionOAuth2AuthorizationRequestRepository` sẽ lưu object này vào `HttpSession`.

   Thực chất Repository này chỉ là lớp bao bọc cho `HttpSession`, thực hiện các thao tác tương đương:

   ```java
   session.setAttribute(
       SPRING_SECURITY_SAVED_AUTHORIZATION_REQUEST,
       authorizationRequest
   );
   ```

   Việc lưu lại Authorization Request giúp Spring Security có thể:

    - đối chiếu `state` khi Google callback để chống CSRF;
    - lấy lại `code_verifier` nhằm hoàn tất PKCE;
    - tiếp tục Authorization Code Flow sau khi người dùng quay trở lại ứng dụng.

5. Sau đó, `OAuth2AuthorizationRequestRedirectFilter` trả về một HTTP **302 Redirect Response**, trong đó header `Location` trỏ tới Authorization Endpoint của Google.

6. Trước khi response được gửi về trình duyệt, **Servlet Container (Tomcat)** kiểm tra xem request hiện tại có vừa tạo `HttpSession` hay không. Nếu có, Tomcat sẽ tự động bổ sung header:

   ```http
   Set-Cookie: JSESSIONID=ABC123; Path=/; HttpOnly
   ```

7. Browser nhận response, lưu cookie `JSESSIONID`, sau đó tự động thực hiện redirect tới Google Authorization Server theo header `Location`.

Kết thúc giai đoạn này:

- Browser đã lưu `JSESSIONID`.
- `HttpSession` đã chứa `OAuth2AuthorizationRequest`.
- Người dùng đã được chuyển sang Google để đăng nhập và cấp quyền.

---

Giải thích

Có thể đọc sơ đồ theo thứ tự từ trên xuống như sau:

1. Sau khi người dùng đăng nhập và đồng ý cấp quyền, Google trả trình duyệt về:

```
GET /login/oauth2/code/google
```

đồng thời browser gửi kèm cookie:

```
JSESSIONID=ABC123
```

2. Tomcat sử dụng `JSESSIONID` để tìm đúng `HttpSession` đã được tạo ở giai đoạn trước.
3. `OAuth2LoginAuthenticationFilter` lấy lại `OAuth2AuthorizationRequest` đã lưu trong `HttpSession` thông qua `HttpSessionOAuth2AuthorizationRequestRepository`.
4. Filter đối chiếu giá trị `state` trong callback với `state` đã lưu trước đó để chống tấn công CSRF, đồng thời lấy lại `code_verifier` để hoàn tất quá trình PKCE.
5. Filter sử dụng **Authorization Code** để gọi **Token Endpoint** của Google và đổi lấy:
    - Access Token;
    - Refresh Token (nếu được cấp);
    - ID Token.
6. Sau khi nhận được ID Token, Spring Security xác thực chữ ký và các claim quan trọng (`iss`, `aud`, `exp`, `nonce`, ...). Nếu hợp lệ, `OidcUserService` sẽ tạo một `OidcUser` đại diện cho người dùng đã đăng nhập.
7. Spring Security tạo một `Authentication` (cụ thể là `OAuth2AuthenticationToken`) với `principal` chính là `OidcUser`.
8. Từ các token vừa nhận được, Spring Security tạo một `OAuth2AuthorizedClient`, đóng gói:
    
    - `ClientRegistration`;
    - `AccessToken`;
    - `RefreshToken`.
    
    Sau đó lưu object này vào `OAuth2AuthorizedClientRepository` (thông qua `AuthenticatedPrincipalOAuth2AuthorizedClientRepository`).
    
9. Đồng thời, `Authentication` được đặt vào `SecurityContext`. Sau khi filter xử lý xong, `SecurityContextHolderFilter` sẽ lưu `SecurityContext` vào `SecurityContextRepository` (mặc định là `HttpSessionSecurityContextRepository`), nên từ các request sau Spring có thể khôi phục trạng thái đăng nhập của người dùng.
10. Cuối cùng, `AuthenticationSuccessHandler` trả về **HTTP 302 Redirect**, chuyển trình duyệt đến URL đích (ví dụ `/profile`) để bắt đầu request mới trong trạng thái đã được xác thực.

> Giai đoạn 4. Lưu trạng thái đăng nhập và OAuth2 Client

Sau khi xác thực thành công, Spring Security sẽ lưu cả trạng thái đăng nhập và thông tin OAuth2 Client để các request sau có thể tái sử dụng.

```
Authentication
        │
        ▼
SecurityContextHolder
        │
        ▼
SecurityContext
        │
        ▼
HttpSessionSecurityContextRepository
        │
session.setAttribute(
    SPRING_SECURITY_CONTEXT,
    securityContext
)

--------------------------------------------

OAuth2AuthorizedClient
        │
        ▼
AuthenticatedPrincipalOAuth2AuthorizedClientRepository
        │
        ▼
OAuth2AuthorizedClientService
(InMemoryOAuth2AuthorizedClientService)
```

 Giải thích

Sau khi đăng nhập thành công, Spring Security sẽ lưu **hai loại dữ liệu hoàn toàn khác nhau**:

**1. SecurityContext**

Được lưu vào `HttpSession` thông qua `HttpSessionSecurityContextRepository`.

Bên trong `SecurityContext` chứa:

- `Authentication`
- `OidcUser`
- Granted Authorities
- các thông tin xác thực khác

Ở các request tiếp theo, `SecurityContextHolderFilter` sẽ đọc lại `SecurityContext` này từ `HttpSession`, vì vậy Controller có thể sử dụng:

```
@AuthenticationPrincipal OidcUser user
```

mà không cần người dùng đăng nhập lại.

**2 . OAuth2AuthorizedClient**

Được lưu thông qua `OAuth2AuthorizedClientRepository`.

Trong dự án này (sử dụng `oauth2Login()`), Repository sẽ ủy quyền cho `OAuth2AuthorizedClientService` (mặc định là `InMemoryOAuth2AuthorizedClientService`) để lưu `OAuth2AuthorizedClient` theo **principal**.

Nhờ đó, ở các request tiếp theo, `OAuth2AuthorizedClientManager` có thể:

- sử dụng Access Token hiện tại nếu còn hiệu lực;
- tự động Refresh Access Token khi hết hạn;
- hoặc khởi động Authorization Code Flow nếu chưa có `OAuth2AuthorizedClient`.

### 3.4. `@RegisteredOAuth2AuthorizedClient` + `OAuth2AuthorizedClientArgumentResolver`

> **Khái niệm:** `@RegisteredOAuth2AuthorizedClient` là annotation dùng để đánh dấu một tham số trong method của Controller, yêu cầu Spring MVC truyền vào một `OAuth2AuthorizedClient` tương ứng với `registrationId`.

Ví dụ:

```java
@GetMapping("/calendars")
public String calendars(
        @RegisteredOAuth2AuthorizedClient("google")
        OAuth2AuthorizedClient client,
        Model model) {

    ...
}
```

Ở đây, `"google"` chính là `registrationId` của `ClientRegistration` đã được khai báo trong `application.properties`.

Tuy nhiên, annotation này **không tự tạo** hay **không tự tìm** `OAuth2AuthorizedClient`.

Việc đó được thực hiện bởi **`OAuth2AuthorizedClientArgumentResolver`**.

Đây là một **`HandlerMethodArgumentResolver`** của Spring MVC.

---

### `HandlerMethodArgumentResolver` là gì?

Trong Spring MVC, trước khi gọi một method của Controller, Spring cần chuẩn bị giá trị cho từng tham số của method.

Ví dụ:

```java
@GetMapping("/profile")
public String profile(
        @AuthenticationPrincipal OidcUser user,
        Model model) {
    ...
}
```

Spring phải biết:

- `OidcUser` lấy từ đâu.
- `Model` lấy từ đâu.

Tương tự:

```java
@GetMapping("/calendars")
public String calendars(
        @RegisteredOAuth2AuthorizedClient("google")
        OAuth2AuthorizedClient client) {
    ...
}
```

Spring cũng phải biết:

- `OAuth2AuthorizedClient` lấy từ đâu.

Việc quyết định **lấy giá trị ở đâu** cho từng tham số được giao cho các **`HandlerMethodArgumentResolver`**.

Một vài Resolver quen thuộc:

- `PathVariableMethodArgumentResolver`
- `RequestParamMethodArgumentResolver`
- `AuthenticationPrincipalArgumentResolver`
- `OAuth2AuthorizedClientArgumentResolver`

Mỗi Resolver chỉ chịu trách nhiệm xử lý một loại tham số nhất định.

---

### `OAuth2AuthorizedClientArgumentResolver` hoạt động như thế nào?

Khi Spring MVC chuẩn bị gọi method của Controller, nó sẽ duyệt qua từng tham số.

Khi gặp:

```java
@RegisteredOAuth2AuthorizedClient("google")
OAuth2AuthorizedClient client
```

Spring sẽ giao việc xử lý cho:

```
OAuth2AuthorizedClientArgumentResolver
```

Resolver sẽ đọc `registrationId = "google"` từ annotation, lấy `Authentication` hiện tại trong `SecurityContext`, sau đó yêu cầu `OAuth2AuthorizedClientManager` cung cấp một `OAuth2AuthorizedClient` hợp lệ.

`OAuth2AuthorizedClientManager` sẽ thực hiện các bước sau:

- Đọc `OAuth2AuthorizedClient` từ `OAuth2AuthorizedClientRepository`.
- Nếu Access Token vẫn còn hiệu lực, trả về ngay.
- Nếu Access Token đã hết hạn nhưng còn Refresh Token, tự động sử dụng Refresh Token để lấy Access Token mới rồi cập nhật lại Repository.
- Nếu chưa có `OAuth2AuthorizedClient`, Manager sẽ khởi động quy trình Authorization để lấy một `OAuth2AuthorizedClient` mới.

Sau khi nhận được kết quả, `OAuth2AuthorizedClientArgumentResolver` sẽ truyền object đó vào tham số `client` của method Controller.

Nhờ vậy, Controller chỉ cần sử dụng:

```java
client.getAccessToken().getTokenValue()
```

để gọi Google API mà **không cần quan tâm**:

- Access Token đang được lưu ở đâu.
- Có cần Refresh Token hay không.
- Access Token vừa được làm mới hay vẫn còn hiệu lực.

---

### Có thể hình dung toàn bộ quá trình như sau

```

      │
      ▼

      │

OAuth2AuthorizedClientManager
      │
      ▼

      │

┌──────────────────────────────────────────────┐
│ Có OAuth2AuthorizedClient ?                  │

      │                                              │

```

---

### Giải thích sơ đồ

Có thể hiểu sơ đồ trên theo thứ tự từ trên xuống như sau:

1. Một request được gửi đến Controller.

2. Trước khi gọi method của Controller, Spring MVC phát hiện tham số được đánh dấu bằng `@RegisteredOAuth2AuthorizedClient`.

3. Spring giao việc tạo tham số này cho `OAuth2AuthorizedClientArgumentResolver`.

4. Resolver lấy `Authentication` hiện tại từ `SecurityContext`, sau đó gọi `OAuth2AuthorizedClientManager` để yêu cầu một `OAuth2AuthorizedClient` hợp lệ.

5. `OAuth2AuthorizedClientManager` đọc `OAuth2AuthorizedClient` từ `OAuth2AuthorizedClientRepository` rồi quyết định:
   - Nếu Access Token vẫn còn hiệu lực thì trả về ngay.
   - Nếu Access Token đã hết hạn nhưng còn Refresh Token thì tự động Refresh rồi lưu lại vào Repository.
   - Nếu chưa có `OAuth2AuthorizedClient`, Manager sẽ khởi động quy trình Authorization để lấy một `OAuth2AuthorizedClient` mới.

6. Sau khi nhận được `OAuth2AuthorizedClient`, `OAuth2AuthorizedClientArgumentResolver` truyền object này vào tham số `client` của method Controller.

7. Controller chỉ việc sử dụng `client.getAccessToken()` để gọi Google Resource Server mà không cần quan tâm Access Token được lấy từ đâu hay có vừa được Refresh hay không.

💡 Trong dự án này, do `SecurityFilterChain` đã cấu hình:

```java
.anyRequest().authenticated()
```

nên khi Controller được gọi, người dùng đã hoàn tất đăng nhập bằng OpenID Connect. Vì vậy, trong hầu hết các trường hợp, `OAuth2AuthorizedClientManager` chỉ cần đọc `OAuth2AuthorizedClient` từ Repository hoặc tự động Refresh Access Token nếu cần, thay vì phải khởi động lại Authorization Code Flow.

## 4. Bảng ánh xạ: thành phần ↔ nhiệm vụ ↔ thay cho gì ở Phase 1

| Thành phần (Phase 2) | Nhiệm vụ | Thay cho (Phase 1 - viết tay) |
|----------------------|----------|-------------------------------|
| `ClientRegistrationRepository` | Giữ thông tin client `google` | `GoogleOidcProperties` |
| `offlineAccessResolver()` | Thêm `access_type=offline` + `prompt=consent` (state + PKCE + nonce do Spring tự sinh) | `PkceUtil` + build URL trong `OidcAuthController` |
| `OAuth2AuthorizationRequestRedirectFilter` | Redirect sang Google (chặng ĐI) | `/oidc/authorize` trong `OidcAuthController` |
| `OAuth2LoginAuthenticationFilter` | Nhận callback, verify state, đổi code lấy token, verify ID Token, tạo `OidcUser` | `/oidc/callback` + `GoogleOidcService` + `IdTokenVerifierService.verify()` |
| `OAuth2AuthorizedClientService` (InMemory) | Lưu token theo principal (phía server) | `session.setAttribute(SESSION_TOKEN, ...)` |
| Spring Boot auto-config (`OAuth2AuthorizedClientManager`) | Auto refresh token khi hết hạn | `TokenService.getValidAccessToken()` |
| `@RegisteredOAuth2AuthorizedClient` | Lấy token cho controller | `tokenService.getValidAccessToken(session)` |
| `@AuthenticationPrincipal OidcUser` | Lấy thông tin user identity | Tự đọc claims từ ID Token |

→ Toàn bộ cột phải (8 chỗ viết tay) đã bị xóa ở Phase 2 và thay bằng cấu hình.

## 5. TẦNG 3 — Hoạt động trong từng chức năng của dự án

### 5.1. Chức năng "Đăng nhập với Google" — khởi động và hoàn tất OIDC Login

Người dùng bấm nút trên `index.html`:

```html
<a href="/oauth2/authorization/google">
    <button>Login with Google</button>
</a>
```

Link này trỏ thẳng tới endpoint **`/oauth2/authorization/google`** — một trong hai endpoint Spring Security tự sinh (mục **3.2**), **không** phải một `@GetMapping` trong Controller. Vì vậy trong dự án **không có** controller nào cho việc đăng nhập; toàn bộ do các Filter của `oauth2Login()` xử lý.

> 💡 Ngoài việc bấm nút, luồng đăng nhập còn có thể được kích hoạt **gián tiếp**: do `SecurityConfig` cấu hình `anyRequest().authenticated()`, nếu người dùng chưa đăng nhập mà truy cập thẳng một URL cần xác thực (ví dụ `/profile`, `/calendars`), Spring Security sẽ tự động chuyển hướng sang `/oauth2/authorization/google`. Cả hai cách đều dẫn vào cùng một luồng dưới đây.

#### Chặng ĐI — khởi động Authorization Code Flow

```
Browser
    │  GET /oauth2/authorization/google
    ▼
OAuth2AuthorizationRequestRedirectFilter
    │
    ├─ offlineAccessResolver tạo OAuth2AuthorizationRequest
    │     • Spring tự sinh: client_id, redirect_uri, scope, response_type,
    │       state, nonce, PKCE (code_verifier, code_challenge)
    │     • resolver thêm: access_type=offline, prompt=consent
    │
    ├─ lưu request vào HttpSession (để đối chiếu state + PKCE khi callback)
    │
    └─ 302 Redirect sang Google
```

Filter này gọi `OAuth2AuthorizationRequestResolver` (bản `offlineAccessResolver` của dự án — mục **2.3**) để dựng request, lưu vào `HttpSession`, rồi trả **302** đưa trình duyệt sang trang đăng nhập/consent của Google.

#### Người dùng đăng nhập + cấp quyền tại Google

Vì có `prompt=consent`, Google luôn hiển thị màn hình xin quyền (gồm cả quyền đọc Calendar theo scope `calendar.readonly`). Sau khi bấm **Allow**, Google redirect về endpoint callback.

#### Chặng VỀ — hoàn tất đăng nhập

```
Google
    │  302 → GET /login/oauth2/code/google?code=...&state=...
    ▼
OAuth2LoginAuthenticationFilter
    │
    ├─ đối chiếu state với giá trị đã lưu trong session (chống CSRF)
    ├─ đổi Authorization Code lấy Access Token + Refresh Token + ID Token
    ├─ verify ID Token (chữ ký qua JWKS + claims iss/aud/exp/nonce)
    ├─ tạo OidcUser  →  lưu Authentication vào SecurityContext
    ├─ tạo OAuth2AuthorizedClient (kèm Refresh Token) → lưu vào Repository (session)
    └─ AuthenticationSuccessHandler
    │
    ▼  vì defaultSuccessUrl("/profile", true)
302 Redirect → /profile
```

`OAuth2LoginAuthenticationFilter` bắt callback và thực hiện toàn bộ phần "lõi" (verify state, đổi token, verify ID Token), tạo `OidcUser` + `OAuth2AuthorizedClient`, rồi nhờ cấu hình `defaultSuccessUrl("/profile", true)` mà chuyển hướng người dùng tới `/profile`.

#### Kết quả — vào thẳng `/profile`

Request mới tới `/profile` giờ đã mang `Authentication` trong `SecurityContext`, nên `ProfileController` nhận trực tiếp `OidcUser`:

```java
@GetMapping("/profile")
public String profile(@AuthenticationPrincipal OidcUser user, Model model) {
    model.addAttribute("user", user);
    return "profile";
}
```

> **Điểm mấu chốt cần nhớ**
>
> - Nút "Login with Google" trỏ tới endpoint **do Spring sinh** (`/oauth2/authorization/google`), **không** có controller riêng.
> - Toàn bộ chặng ĐI (redirect sang Google) và chặng VỀ (đổi code, verify ID Token, tạo `OidcUser` + `OAuth2AuthorizedClient`) do **hai Filter của `oauth2Login()`** đảm nhiệm.
> - Sau khi đăng nhập, người dùng được đưa thẳng tới `/profile`; từ đây `OAuth2AuthorizedClient` (kèm Refresh Token) đã sẵn sàng cho các chức năng Calendar (mục 5.2).
>
> Khác với mô hình "lazy authorization" (chỉ dùng `@RegisteredOAuth2AuthorizedClient` mà không bật `oauth2Login`), ở đây đăng nhập được **kích hoạt tường minh** qua `oauth2Login()`, nên **không có** chuyện một URL bị xử lý hai lần.

### 5.2. Chức năng xem lịch / sự kiện — sử dụng Access Token để gọi Google API

Sau khi người dùng đã hoàn thành Authorization Code Flow, `OAuth2AuthorizedClient` đã được lưu ở kho token phía server (`OAuth2AuthorizedClientService`, theo principal — xem mục 2.4).

Vì vậy, ở các request tiếp theo, Controller chỉ cần khai báo:

```java
@GetMapping("/calendars")
public String calendars(
        @RegisteredOAuth2AuthorizedClient("google") OAuth2AuthorizedClient client,
        Model model) {

    String accessToken = client.getAccessToken().getTokenValue();

    CalendarListResponse calendars =
            calendarService.listCalendars(accessToken);

    ...
}
```

Trước khi method được thực thi, `OAuth2AuthorizedClientArgumentResolver` sẽ lấy `OAuth2AuthorizedClient` từ `OAuth2AuthorizedClientManager` và truyền vào tham số `client`.

Do đó, Controller chỉ việc lấy Access Token thông qua:

```
String accessToken = client.getAccessToken().getTokenValue();
```

sau đó truyền cho tầng Service để gọi Google Calendar API.

---

> **GoogleCalendarService sử dụng Access Token như thế nào?**

Trong `GoogleCalendarService`, Access Token được gắn vào HTTP Header theo chuẩn **Bearer Token**:

```java
return restClient.get()
        .uri(CALENDAR_LIST_URI)
        .header(HttpHeaders.AUTHORIZATION, "Bearer " + accessToken)
        .retrieve()
        .body(CalendarListResponse.class);
```

Khi gửi request, HTTP Request sẽ có dạng:

```HTTP
GET https://www.googleapis.com/calendar/v3/users/me/calendarList
Authorization: Bearer eyJhbGciOi...
```

Google Resource Server sẽ đọc Access Token từ header `Authorization` để xác thực người dùng, kiểm tra quyền truy cập (`scope`), sau đó mới trả về danh sách Calendar.

---

> **Điều gì xảy ra nếu Access Token đã hết hạn?**

Controller và `GoogleCalendarService` **không cần quan tâm** Access Token còn hạn hay không.

Mỗi khi gặp tham số:

```java
@RegisteredOAuth2AuthorizedClient("google")
OAuth2AuthorizedClient client
```

Spring đều giao việc lấy `OAuth2AuthorizedClient` cho `OAuth2AuthorizedClientManager`.

Manager sẽ tự kiểm tra trạng thái của Access Token:

- Nếu Access Token vẫn còn hiệu lực → sử dụng ngay.
- Nếu Access Token đã hết hạn nhưng có Refresh Token → tự động lấy Access Token mới rồi mới truyền `OAuth2AuthorizedClient` vào Controller.
- Nếu chưa có `OAuth2AuthorizedClient` → khởi động Authorization Code Flow để người dùng đăng nhập Google.

Nhờ đó, khi Controller bắt đầu thực thi, `client.getAccessToken()` luôn là **Access Token hợp lệ**.

---

> Có thể hình dung toàn bộ quá trình như sau

```
Browser
    │
GET /calendars
    │
    ▼
Controller
    │
    ▼
@RegisteredOAuth2AuthorizedClient
    │
    ▼
OAuth2AuthorizedClientArgumentResolver
    │
    ▼
OAuth2AuthorizedClientManager
    │
    ├── Access Token còn hạn
    │         │
    │         ▼
    │   Trả OAuth2AuthorizedClient
    │
    └── Access Token hết hạn
              │
              ▼
      Refresh Access Token
              │
              ▼
      Trả OAuth2AuthorizedClient
              │
              ▼
Controller
    │
client.getAccessToken()
    │
    ▼
GoogleCalendarService
    │
Authorization: Bearer <access_token>
    │
    ▼
Google Calendar API
```

---

> **Điểm mấu chốt cần nhớ**

Điểm quan trọng nhất của cơ chế này là **Controller không trực tiếp quản lý Access Token**. Controller chỉ nhận một `OAuth2AuthorizedClient` đã được Spring chuẩn bị sẵn và sử dụng:

```
client.getAccessToken()
```

để gọi Google API.

Toàn bộ việc:

- lấy `OAuth2AuthorizedClient` từ `OAuth2AuthorizedClientService` (kho token phía server),
- kiểm tra Access Token còn hạn hay không,
- tự động Refresh Access Token khi cần,
- hoặc khởi động Authorization Code Flow nếu chưa có token,

đều được Spring Security xử lý phía sau thông qua `OAuth2AuthorizedClientArgumentResolver` và `OAuth2AuthorizedClientManager`.

### 5.3. Chức năng auto-refresh — Access Token hết hạn

Access Token do Google cấp chỉ có thời gian sống khoảng **1 giờ**. Sau khi hết hạn, người dùng vẫn có thể tiếp tục sử dụng ứng dụng mà **không cần đăng nhập hay cấp quyền lại**.

Ví dụ, người dùng truy cập:

```HTTP
GET /calendars
```

Controller vẫn giữ nguyên:

```java
@GetMapping("/calendars")
public String calendars(
        @RegisteredOAuth2AuthorizedClient("google")
        OAuth2AuthorizedClient client,
        Model model) {

    String accessToken = client.getAccessToken().getTokenValue();

    CalendarListResponse calendars =
            calendarService.listCalendars(accessToken);

    ...
}
```

Điểm khác biệt là **trước khi Controller được thực thi**, `OAuth2AuthorizedClientArgumentResolver` sẽ tiếp tục yêu cầu `OAuth2AuthorizedClientManager` cung cấp một `OAuth2AuthorizedClient` hợp lệ.

Lần này, Manager phát hiện:

- đã có `OAuth2AuthorizedClient` trong kho token (`OAuth2AuthorizedClientService`);
- nhưng **Access Token đã hết hạn**;
- và vẫn còn **Refresh Token**.

Nhờ Spring Boot **auto-config**, `OAuth2AuthorizedClientManager` mặc định đã có sẵn các provider `authorizationCode` + `refreshToken` (+ `clientCredentials`) — **dự án không cần tự khai báo bean nào** cho việc này.

Vì `OAuth2AuthorizedClient` đang có sẵn **Refresh Token** (nhờ `access_type=offline` ở mục **2.3**), `OAuth2AuthorizedClientManager` sẽ giao việc cho `RefreshTokenOAuth2AuthorizedClientProvider`.

Provider này tự động gửi request đến **Token Endpoint** của Google với:

- `grant_type=refresh_token`
- `refresh_token`
- `client_id`
- `client_secret` (nếu cần)

để đổi lấy **Access Token mới**.

Sau khi nhận được Access Token mới, Spring sẽ cập nhật lại `OAuth2AuthorizedClient` trong `OAuth2AuthorizedClientService` (bộ nhớ phía server, theo principal), rồi mới trả `OAuth2AuthorizedClient` cho Controller.

Vì vậy, khi Controller bắt đầu thực thi:

```java
String accessToken = client.getAccessToken().getTokenValue();
```

thì `accessToken` đã là **Access Token mới**, hoàn toàn hợp lệ để gọi Google Calendar API.

> **Có thể hình dung toàn bộ quá trình như sau**

```

      │
      ▼
OAuth2AuthorizedClientArgumentResolver
      │
      ▼
OAuth2AuthorizedClientManager
      │
      ▼
Đọc OAuth2AuthorizedClient từ AuthorizedClientService
      │
      ▼
Access Token hết hạn?
      │
      ├── Không
      │      │
      │      ▼
      │  Trả OAuth2AuthorizedClient
      │
      └── Có
             │
             ▼
RefreshTokenOAuth2AuthorizedClientProvider
             │
             ▼
POST /token
(grant_type=refresh_token)
             │
             ▼
Google Token Endpoint
             │
             ▼
Access Token mới
             │
             ▼
Cập nhật OAuth2AuthorizedClient
trong AuthorizedClientService
             │
             ▼
Trả OAuth2AuthorizedClient
             │
             ▼
Controller
             │
             ▼
Google Calendar API
```

---

> **Điểm mấu chốt cần nhớ**

Điều quan trọng là **Controller hoàn toàn không biết** Access Token đã từng hết hạn.

Khi Controller nhận được:

```java
@RegisteredOAuth2AuthorizedClient
OAuth2AuthorizedClient client
```

thì Spring Security đã đảm bảo `client` luôn chứa **Access Token còn hiệu lực**.

Toàn bộ quá trình:

- kiểm tra thời hạn của Access Token,
- sử dụng Refresh Token để lấy Access Token mới,
- cập nhật lại `OAuth2AuthorizedClient` trong `OAuth2AuthorizedClientService`,

đều được Spring Security thực hiện tự động trước khi Controller bắt đầu chạy.

Đây chính là ý nghĩa của **auto-refresh** hay **refresh trong suốt (transparent refresh)**: người dùng vẫn sử dụng ứng dụng bình thường, không cần đăng nhập hay cấp quyền lại, còn Controller cũng không phải viết bất kỳ đoạn mã nào để kiểm tra hoặc refresh Access Token.

### 5.4. `state` và PKCE bảo vệ điều gì (nhắc lại nhanh)

- **`state`**: Spring tự sinh, lưu trong session, đối chiếu ở callback (mục 3.3b) → chống **CSRF / callback giả mạo**.
- **PKCE** (`code_verifier`/`code_challenge`): kẻ tấn công dù cướp được `code` cũng **không đổi được token** vì không biết `code_verifier` → chống **đánh cắp authorization code**.

Hai cơ chế này ở Phase 1 ta tự làm trong `PkceUtil` + `AuthController`; ở Phase 2 do resolver (mục 2.3) và filter (mục 3.3) lo, Spring tự sinh và xử lý.

## 6. Tóm tắt một câu cho mỗi thành phần

- `permitAll()` (chỉ cho `/`, `/error`) + `anyRequest().authenticated()` → mở trang chủ/lỗi công khai, còn lại buộc đăng nhập; truy cập URL cần auth khi chưa login sẽ tự kích hoạt `oauth2Login`.
- `oauth2Login()` → bật chế độ **OIDC Login**, tạo `OidcUser` và `Authentication`.
- `authorizationRequestResolver` + `offlineAccessResolver()` → tùy biến request gửi Google (thêm `access_type=offline` + `prompt=consent`).
- `OAuth2AuthorizedClientManager` (auto-config, có sẵn provider `refreshToken`) → tự lấy/refresh token cho controller.
- **Phần ẩn** (`ClientRegistrationRepository`, 2 filter, 2 endpoint, `AuthorizedClientRepository`, argument resolver) → Spring tự dựng; config của ta chỉ cắm vào và tinh chỉnh.

> Hiểu đúng `SecurityConfig` = hiểu rằng **ta đang cấu hình một cỗ máy có sẵn**, chứ không tự viết cỗ máy đó. Ngắn là vì phần lớn đã được Spring làm sẵn bên dưới.
