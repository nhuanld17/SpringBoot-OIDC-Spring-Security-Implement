# Luồng Refresh Token — Kiểm tra hết hạn + Refresh Grant + Merge

`access_token` do Google cấp chỉ sống **ngắn hạn** (~1 giờ, `expires_in ≈ 3599`). Khi gọi Calendar API (doc #4), nếu token đã/sắp hết hạn, ứng dụng phải **xin một access token mới** mà **không cần** người dùng consent lại. Việc này dùng **refresh token** (được cấp ở bước callback nhờ `access_type=offline`, xem doc #2, #3).

Luồng này có **hai cách kích hoạt**:
1. **Tự động** — mỗi lần `getValidAccessToken(session)` thấy token sắp hết hạn (doc #4 gọi hàm này trước khi gọi API).
2. **Thủ công** — người dùng bấm nút "Refresh" → `GET /oidc/refresh` (endpoint demo ép refresh ngay, nằm trong `OidcAuthController`).

Cả hai đều đi về cùng một hàm `TokenService.refresh(...)`.

## Vị trí trong toàn bộ flow

```
[/oidc/callback]  (doc #3)  ── lưu access_token + refresh_token + expiresAt
        │
        ▼
[/calendars] [/events]  (doc #4)  ── gọi getValidAccessToken()
        │                                  │
        │                                  └── sắp hết hạn? ──▶ refresh()  <== DOC NÀY
        │                                                                │
[/oidc/refresh]  ───────────────────────────────────────────────────────┘ (cùng hàm refresh)
        │
        ▼
   refreshed.html  (hoặc error-page nếu refresh token hỏng)
```

Điểm mấu chốt: **refresh grant là một lời gọi server-to-server khác tới token endpoint của Google**, dùng `grant_type=refresh_token` thay vì `authorization_code`. Trình duyệt **không** tham gia vào bước này (trừ endpoint demo `/oidc/refresh` là do người dùng chủ động gọi).

## Chi tiết từng bước (kèm code trong dự án)

### Bước 1 — Kiểm tra hết hạn (`getValidAccessToken`)

Mọi lời gọi API đều đi qua hàm này trước (doc #4). Nó quyết định token còn dùng được không, hay phải refresh:

```java
// TokenService.getValidAccessToken()
public String getValidAccessToken(HttpSession session) {
    TokenResponse token = (TokenResponse) session.getAttribute(OidcAuthController.SESSION_TOKEN);

    if (token == null || token.access_token() == null) {
        return null;   // chưa uỷ quyền -> controller redirect "/"
    }

    Instant expiresAt = (Instant) session.getAttribute(OidcAuthController.SESSION_EXPIRES_AT);

    // Còn hạn thoải mái (> 60s nữa mới hết) -> dùng luôn, KHÔNG refresh
    if (expiresAt != null &&
            Instant.now().isBefore(expiresAt.minusSeconds(60))) {
        return token.access_token();
    }

    // Đã hết hạn hoặc sắp hết hạn (< 60s)
    if (token.refresh_token() == null) {
        return token.access_token();   // không có refresh -> đành dùng tạm (sẽ bị 401)
    }

    // Có refresh token -> tự động refresh
    System.out.println(">>> Access token sắp hết hạn -> đang refresh ...");
    try {
        return refresh(session, token).access_token();
    } catch (RestClientException e) {
        // refresh token hỏng -> xoá sạch, buộc đăng nhập lại
        session.removeAttribute(OidcAuthController.SESSION_TOKEN);
        session.removeAttribute(OidcAuthController.SESSION_EXPIRES_AT);
        return null;   // controller sẽ redirect về "/"
    }
}
```

#### Tại sao "còn hạn thoải mái" là `expiresAt - 60s`?

```
expiresAt (ví dụ 10:00:00)
   │
   │  ────────────────┬───────────────┬───────────────
   │   dùng thoải mái  │  vùng 60s     │  đã hết hạn
   │                  │  "sắp hết"    │
   │             expiresAt - 60s  (09:59:00)      now
```

- Nếu `now < expiresAt - 60s` → token còn đủ dài để phục vụ request hiện tại → **không refresh** (tránh gọi Google mỗi lần).
- Nếu `now >= expiresAt - 60s` → token có thể hết ngay khi request đang chạy → **refresh ngay** để lấy token mới an toàn.

> Con số 60 giây gọi là **skew/leeway**: bù cho độ trễ mạng và chênh lệch đồng hồ giữa server và Google.

#### Nếu không có `refresh_token` thì sao?

Ở bước callback (doc #3), refresh token chỉ có khi `access_type=offline` + `prompt=consent` (doc #2). Nếu vì lý do nào đó `refresh_token == null`, code **chấp nhận trả access token cũ** — request gọi API sẽ bị Google trả **401 Invalid Credentials**, và controller (doc #4) bắt lỗi đó để hiện `error-page`. Không throw exception ở đây để không phá luồng khi chưa chắc chắn token hỏng.

### Bước 2 — Gửi Refresh Grant (`refreshAccessToken`)

Khi cần refresh, `TokenService.refresh` gọi `GoogleOidcService.refreshAccessToken`:

```java
// GoogleOidcService.refreshAccessToken()
public TokenResponse refreshAccessToken(String refreshToken) {
    MultiValueMap<String, String> form = new LinkedMultiValueMap<>();

    form.add("grant_type", "refresh_token"); // <== KHÁC với authorization_code
    form.add("refresh_token", refreshToken);
    form.add("client_id", props.clientId());
    form.add("client_secret", props.clientSecret());

    return restClient.post()
            .uri(props.tokenUri())                              // https://oauth2.googleapis.com/token
            .contentType(MediaType.APPLICATION_FORM_URLENCODED)
            .body(form)
            .retrieve()
            .body(TokenResponse.class);
}
```

So sánh với exchange code (doc #3):

| Tham số | Exchange code (doc #3) | Refresh grant (bước này) |
|---------|------------------------|--------------------------|
| `grant_type` | `authorization_code` | `refresh_token` |
| `code` / `code_verifier` | Có (PKCE) | **Không** — không cần code, không cần PKCE |
| `refresh_token` | Không | **Có** |
| `redirect_uri` | Có (phải khớp) | **Không** — refresh grant không dùng redirect_uri |
| `client_id` + `client_secret` | Có | Có (chứng thực client) |

```
        Backend  ──HTTPS POST (kín, server-to-server)──▶  Google /token
                     grant_type=refresh_token,             │
                     refresh_token, client_id,             │ Google kiểm:
                     client_secret                         │  - refresh_token hợp lệ & chưa bị thu hồi?
                                                            │  - client_id/secret đúng?
        TokenResponse  ◀───────────── JSON ───────────────┘
```

> Refresh grant **nhẹ hơn** exchange code: không cần `redirect_uri`, không cần PKCE (`code_verifier`), vì refresh token bản thân đã là "giấy uỷ quyền dài hạn" được cấp sau khi user đã consent một lần.

### Bước 3 — Merge token (giữ refresh token cũ) ⭐

Đây là chi tiết **quan trọng nhất** của luồng này. Google **thường KHÔNG trả refresh token mới** trong response của refresh grant (chỉ trả `access_token`, `expires_in`, `scope`, `token_type`). Nếu ta ghi đè nguyên response vào session, `refresh_token` sẽ bị mất → lần sau không refresh được nữa.

```java
// TokenService.refresh()
public TokenResponse refresh(HttpSession session, TokenResponse currentToken) {
    TokenResponse refreshedToken = oidcService.refreshAccessToken(currentToken.refresh_token());

    // Google KHÔNG TRẢ refresh token mới -> giữ lại cái cũ
    TokenResponse merged = new TokenResponse(
            refreshedToken.access_token(),                       // access token MỚI
            refreshedToken.expires_in(),                         // thời gian sống MỚI
            currentToken.refresh_token(),                        // ⭐ VẪN GIỮ refresh token CŨ
            refreshedToken.scope() != null ? refreshedToken.scope() : currentToken.scope(),
            refreshedToken.token_type(),
            refreshedToken.id_token()
    );

    session.setAttribute(OidcAuthController.SESSION_TOKEN, merged);
    session.setAttribute(OidcAuthController.SESSION_EXPIRES_AT,
            Instant.now().plusSeconds(refreshedToken.expires_in()));

    return merged;
}
```

Cơ chế merge:

```
currentToken (trong session)          refreshedToken (từ Google)
┌──────────────────────────┐          ┌──────────────────────────┐
│ access_token  = A (cũ)   │          │ access_token  = A' (mới) │
│ expires_in    = 3599     │          │ expires_in    = 3599     │
│ refresh_token = R  ⭐     │   ───▶   │ refresh_token = null ❌  │  (Google thường không trả)
│ scope         = ...      │          │ scope         = ...      │
└──────────────────────────┘          └──────────────────────────┘
            │                                      │
            └──────────────┬───────────────────────┘
                           ▼
                  merged (ghi đè session)
            ┌──────────────────────────┐
            │ access_token  = A' (mới) │
            │ expires_in    = 3599     │
            │ refresh_token = R  ⭐     │  <== giữ nguyên cái cũ
            │ scope         = ...      │
            └──────────────────────────┘
```

Sau khi merge, ứng dụng cập nhật lại:
- `oidc_token` = `merged` (access token mới, refresh token cũ).
- `oidc_expires_at` = `now + expires_in` (mốc hết hạn mới).

> ⚠️ **Nguyên tắc vàng**: refresh token là "tài sản dài hạn", chỉ được cấp một lần (lúc consent). Mỗi lần refresh grant, **phải copy refresh token cũ sang object mới**. Quên bước này là lỗi kinh điển khi làm OAuth2.

> Lưu ý: `merged` cũng chép lại `id_token` từ response. Refresh grant của Google **có thể** trả kèm một `id_token` mới; nếu không, giá trị này là `null` — dự án chỉ dùng access/refresh token cho Calendar nên không verify lại id_token ở bước refresh.

### Bước 4 — Endpoint demo thủ công (`/oidc/refresh`)

Ngoài tự động, dự án có endpoint cho phép ép refresh để demo (trong `OidcAuthController`):

```java
// OidcAuthController.forceRefresh()
@GetMapping("/oidc/refresh")
public String forceRefresh(HttpSession session, Model model) {
    TokenResponse current = (TokenResponse) session.getAttribute(SESSION_TOKEN);
    if (current == null || current.refresh_token() == null) {
        model.addAttribute("error", "Chưa có refresh token - hãy connect lại");
        return "error-page";
    }

    String oldAccess = current.access_token();
    TokenResponse refreshed;
    try {
        refreshed = tokenService.refresh(session, current);  // cùng hàm refresh() ở trên
    } catch (RestClientResponseException ex) {
        session.removeAttribute(SESSION_TOKEN);
        session.removeAttribute(SESSION_EXPIRES_AT);
        session.removeAttribute(SESSION_USER);
        model.addAttribute("error",
                "Refresh token không còn hợp lệ (có thể đã bị thu hồi). Hãy connect lại.");
        return "error-page";
    }

    // So sánh 20 ký tự đầu để thấy token ĐÃ ĐỔI (Math.min tránh lỗi khi token ngắn)
    model.addAttribute("oldPrefix", oldAccess.substring(0, Math.min(20, oldAccess.length())) + "...");
    model.addAttribute("newPrefix", refreshed.access_token().substring(0, Math.min(20, refreshed.access_token().length())) + "...");
    model.addAttribute("newExpiresIn", refreshed.expires_in());

    return "refreshed";
}
```

Trang `refreshed.html` hiển thị 20 ký tự đầu của access token cũ/mới để người dùng thấy token thực sự đã được đổi.

> Khác biệt nhỏ so với đường tự động: `forceRefresh()` bắt `RestClientResponseException` (lỗi có HTTP status từ Google) rồi hiển thị `error-page`, và dọn thêm cả `SESSION_USER`; còn `getValidAccessToken()` bắt `RestClientException` (rộng hơn) rồi trả `null` để controller redirect `/`.

## Xử lý khi refresh token hỏng

Refresh token có thể bị vô hiệu vì:
- Người dùng thu hồi quyền truy cập trong [Google Account settings](https://myaccount.google.com/permissions).
- Quá nhiều refresh token được cấp (Google giới hạn số lượng; các token cũ tự hết hiệu lực).
- Refresh token không được dùng trong thời gian rất dài (chính sách của Google).

Khi đó Google trả lỗi (thường **400 / 401** với `invalid_grant`). Dự án xử lý bằng cách **xoá session** và bắt người dùng đăng nhập lại:

## Tóm tắt các key session liên quan

| Key session | Giá trị | Ghi chú |
|-------------|---------|---------|
| `oidc_token` (`SESSION_TOKEN`) | `TokenResponse` | Chứa access + refresh token; bị **ghi đè** mỗi lần refresh |
| `oidc_expires_at` (`SESSION_EXPIRES_AT`) | `Instant` | Thời điểm access token hết hạn; tính lại sau mỗi refresh |
| `oidc_user` (`SESSION_USER`) | `AuthenticatedUser` | Danh tính đã verify; bị dọn khi refresh token hỏng (đường thủ công) |

## Hai lỗi hay gặp ở bước này

1. **Mất refresh token sau merge** — quên copy `currentToken.refresh_token()` sang object mới → lần sau gọi API bị 401 vĩnh viễn, phải consent lại. (Xem Bước 3.)
2. **Refresh quá thường xuyên** — nếu bỏ qua vùng leeway 60s, mỗi request lại gọi Google một lần → lãng phí và dễ chạm rate limit. Để token "còn hạn thoải mái" thì dùng luôn, chỉ refresh khi sắp hết.
