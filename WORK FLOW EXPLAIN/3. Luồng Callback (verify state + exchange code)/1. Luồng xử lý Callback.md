# Luồng Callback — Verify state + Đổi code lấy Token + Verify ID Token

Sau khi người dùng bấm **"Allow"** trên trang consent, Google **redirect trình duyệt** quay về ứng dụng kèm `authorization code` và `state`. Đây là bước biến "authorization code" thành "token", đồng thời **xác thực danh tính** người dùng qua ID Token (OIDC).

Endpoint phụ trách: `GET /oidc/callback` trong `OidcAuthController`.

---

## Vị trí trong toàn bộ flow

```
[/oidc/authorize]      (doc #2)
        │
        ▼
   Google consent  ── người dùng bấm "Allow"
        │
        │  302 redirect:
        │  /oidc/callback?code=4/0Ae...&state=S
        ▼
[/oidc/callback]       <-- DOC NÀY
        │
        ├── verify state
        ├── exchange code -> token   (server-to-server tới Google)
        ├── verify ID token          (chữ ký + claims + nonce)
        └── lưu user + token vào session
        │
        ▼
   connected.html
        │
        ▼
   Calendar API          (doc #4)
```

Điểm cần nhớ: **việc đổi `code` lấy token diễn ra server-to-server** (backend gọi thẳng token endpoint của Google), **không** đi qua trình duyệt. Trình duyệt chỉ mang `code` về tới backend rồi dừng.

Khác với OAuth2 thuần: vì đây là OIDC (`scope` có `openid`), token trả về kèm một **ID Token** (JWT danh tính). Ta **bắt buộc phải verify** nó trước khi tin — đây là điểm mấu chốt của bước callback.

---

## Toàn cảnh sơ đồ

```
Google  ──302──▶  Browser  ──GET /oidc/callback?code=...&state=...──▶  OidcAuthController.callback()
                                                                                │
   0. Có ?error=... ?  (user bấm Cancel)                                        │
        └── có  ->  error-page                                                  │
                                                                                │
   1. Verify state:  state(param) == oidc_state(session) ?                      │
        └── không khớp  ->  error-page   (chống CSRF)                           │
                                                                                │
   2. Lấy code_verifier (PKCE) + expectedNonce từ session                       │
                                                                                │
   3. Exchange code -> token:                                                   │
        POST https://oauth2.googleapis.com/token                               ─┼──▶ Google token endpoint
            grant_type=authorization_code                                       │      (kiểm code + SHA256(verifier)==challenge
            code, redirect_uri, code_verifier,                                  │       + client_id/secret)
            client_id, client_secret                                           ◀┼──── trả JSON: access_token, refresh_token,
                                                                                │       id_token, expires_in, scope, token_type
   4. Có id_token không?  -> không thì error-page                               │
                                                                                │
   5. Verify ID token:  chữ ký (JWKS) + iss + aud + exp/iat + nonce            ─┼──▶ Google JWKS endpoint (lấy public key)
        └── sai bất kỳ điều gì  ->  error-page                                  │
                                                                                │
   6. Lưu user (từ ID token) + token + tính expiresAt vào session              │
   7. Dọn state + nonce + code_verifier (dùng 1 lần)                            │
   8. render connected.html                                                     │
```

## Chi tiết từng bước (kèm code trong dự án)

Chữ ký method:

```java
@GetMapping("/oidc/callback")
public String callback(
        @RequestParam(required = false) String code,
        @RequestParam(required = false) String state,
        @RequestParam(required = false) String error,
        HttpSession session,
        Model model
) {
```

Google gọi lại URL này với các query param `code`, `state` (khi thành công) hoặc `error` (khi thất bại/bị từ chối). Để `required = false` để tự xử lý thay vì để Spring văng lỗi khi thiếu.

### Bước 0 — Người dùng từ chối (`?error=...`)

```java
if (error != null) {
    model.addAttribute("error", "Google tra ve loi: " + error);
    return "error-page";
}
```

Nếu người dùng bấm **Cancel/Deny** ở màn consent, Google redirect về `/oidc/callback?error=access_denied`. Ta hiển thị trang lỗi thay vì cố xử lý tiếp.

### Bước 1 — Verify `state` (chống CSRF)

```java
String savedState = (String) session.getAttribute(SESSION_STATE);
if (savedState == null || !savedState.equals(state)) {
    model.addAttribute("error", "State khong khop -> nghi ngo CSRF. Tu choi.");
    return "error-page";
}
```

`state` trên URL **phải khớp** với `oidc_state` đã lưu trong session ở bước authorize. Không khớp ⇒ callback không do phiên này khởi tạo ⇒ từ chối. (Cơ chế chi tiết xem doc #2 — mục "state chống CSRF".)

### Bước 2 — Lấy `code_verifier` (PKCE) và `expectedNonce` từ session

```java
String codeVerifier  = (String) session.getAttribute(SESSION_CODE_VERIFIER);
String expectedNonce = (String) session.getAttribute(SESSION_NONCE);
```

- `code_verifier`: bí mật PKCE, sắp "xuất trình" cho Google để chứng minh chính client này đã khởi tạo request.
- `expectedNonce`: giá trị `nonce` đã sinh ở authorize; lát nữa dùng để **so với claim `nonce` bên trong ID Token** (chống replay).

> Nếu các giá trị này `null` nghĩa là session đã mất (ví dụ restart app giữa chừng) → bước đổi token sẽ thất bại với `invalid_grant: Missing code verifier`, hoặc verify nonce sẽ không khớp.

### Bước 3 — Đổi `code` lấy token (server-to-server)

```java
TokenResponse token;
try {
    token = oidcService.exchangeCodeForToken(code, codeVerifier);
} catch (RestClientResponseException ex) {
    model.addAttribute("error", "Doi code lay token that bai ("
            + ex.getStatusCode().value() + "): " + ex.getResponseBodyAsString());
    return "error-page";
}
```

Chi tiết lời gọi trong `GoogleOidcService`:

```java
public TokenResponse exchangeCodeForToken(String code, String codeVerifier) {
    MultiValueMap<String, String> form = new LinkedMultiValueMap<>();
    form.add("grant_type", "authorization_code"); // dạng đổi code
    form.add("code", code);                        // code Google vừa trả về
    form.add("redirect_uri", props.redirectUri()); // phải trùng lúc authorize
    form.add("code_verifier", codeVerifier);       // PKCE: bí mật gốc
    form.add("client_id", props.clientId());
    form.add("client_secret", props.clientSecret());

    return restClient.post()
            .uri(props.tokenUri())                                  // https://oauth2.googleapis.com/token
            .contentType(MediaType.APPLICATION_FORM_URLENCODED)     // body dạng x-www-form-urlencoded
            .body(form)
            .retrieve()
            .body(TokenResponse.class);
}
```

Những điểm bản chất:

| Tham số gửi lên token endpoint | Vai trò |
|---|---|
| `grant_type=authorization_code` | Nói với Google "tôi đang đổi authorization code" |
| `code` | Chính code Google vừa trả về callback |
| `redirect_uri` | Phải **trùng khít** với `redirect_uri` lúc authorize, nếu lệch → `redirect_uri_mismatch` |
| `code_verifier` | Bí mật PKCE gốc; Google so `SHA256(code_verifier)` với `code_challenge` đã lưu |
| `client_id` + `client_secret` | Chứng thực client (web app confidential) |

```
        Backend  ──HTTPS POST (kín, server-to-server)──▶  Google /token
                     grant_type, code, code_verifier,       │
                     redirect_uri, client_id, client_secret │
                                                            │ Google kiểm:
                                                            │  - code hợp lệ & chưa dùng?
                                                            │  - SHA256(code_verifier)==challenge?
                                                            │  - client_id/secret đúng?
        TokenResponse  ◀───────────── JSON ───────────────┘
```

Cấu trúc JSON trả về được map vào record `TokenResponse` (tên field trùng key JSON):

```java
public record TokenResponse(
        String access_token,   // token ngắn hạn để gọi Calendar API
        Integer expires_in,    // số giây còn sống của access token (~3599)
        String refresh_token,  // token dài hạn để xin access token mới (có vì access_type=offline)
        String scope,          // quyền thực tế được cấp
        String token_type,     // "Bearer"
        String id_token        // JWT danh tính người dùng (OIDC) — sẽ được verify ở bước 5
) {}
```

#### Vì sao phải gửi lại `redirect_uri` — dù bước này KHÔNG hề redirect?

Đây là chỗ dễ thắc mắc: bước đổi token là backend gọi **thẳng** tới token endpoint (không có cú redirect nào cả), vậy tại sao vẫn phải kèm `redirect_uri`?

Câu trả lời: ở bước này `redirect_uri` **không dùng để chuyển hướng** — nó đóng vai trò một **giá trị để Google đối chiếu (verification)**. Theo chuẩn OAuth2 (RFC 6749 §4.1.3), nếu authorization request lúc đầu có gửi `redirect_uri`, thì token request **bắt buộc** gửi lại **y hệt** giá trị đó.

Cơ chế:

```
Lúc authorize (doc #2):
    Google phát ra  code  và GHI NHỚ:  code  ⇄  redirect_uri = R
                                                 (kèm client_id, code_challenge)

Lúc đổi token (bước này):
    Backend gửi lên:  code + redirect_uri = R'
    Google kiểm:      R' == R ?
        ├── khớp     -> tiếp tục cấp token
        └── lệch     -> từ chối: "redirect_uri_mismatch"
```

Nghĩa là Google "chốt" `redirect_uri` ngay từ lúc phát code, rồi lúc đổi token nó so lại để chắc chắn **cùng một `redirect_uri`** xuyên suốt. Trong dự án giá trị này là `http://localhost:8080/oidc/callback`.

**Mục đích bảo mật:** buộc authorization code gắn chặt với đúng `redirect_uri` ban đầu → thêm một lớp chống **authorization code injection**. Nếu token endpoint *không* kiểm giá trị này, kẻ tấn công có thể lấy một code (vốn được phát cho `redirect_uri` hợp lệ) rồi đem đổi token trong một ngữ cảnh/redirect khác.

> Tóm lại: `redirect_uri` lúc authorize = "hãy trả code về đây"; `redirect_uri` lúc đổi token = "bằng chứng rằng code này đúng là được phát cho địa chỉ đó". Cùng một giá trị, hai vai trò khác nhau — và phải **trùng khít** (bao gồm cả `http`/`https`, cổng, dấu `/` cuối).

### Bước 4 — Chắc chắn có `id_token`

```java
if (token == null || token.id_token() == null) {
    model.addAttribute("error", "Khong nhan duoc id_token tu Google.");
    return "error-page";
}
```

Vì đây là luồng OIDC, ta **kỳ vọng** Google trả về `id_token`. Nếu thiếu (thường do `scope` không có `openid`), coi như luồng đăng nhập thất bại.

### Bước 5 — Verify ID Token (chữ ký + claims + nonce) — trái tim của OIDC

```java
AuthenticatedUser user;
try {
    user = idTokenVerifierService.verify(token.id_token(), expectedNonce);
} catch (RuntimeException ex) {
    model.addAttribute("error", "ID token khong hop le: " + ex.getMessage());
    return "error-page";
}
```

ID Token là một JWT gồm 3 phần `header.payload.signature`. **Không được tin** nội dung của nó cho tới khi kiểm tra xong. `IdTokenVerifierService.verify(idToken, expectedNonce)` thực hiện lần lượt:

```
1) Chữ ký (RS256):
     - header.alg phải là "RS256", header phải có "kid"
     - lấy public key của Google theo kid (từ JWKS endpoint) -> verify chữ ký của header.payload
     - sai chữ ký  ->  từ chối ("co the bi gia mao")

2) Claims:
     - iss  ∈ issuer hợp lệ (https://accounts.google.com)
     - aud  == client_id của app        (token này cấp cho ĐÚNG app mình)
     - exp  chưa hết hạn (có CLOCK_SKEW) (token còn sống)
     - iat  không nằm ở tương lai
     - nonce == expectedNonce trong session  (chống replay ID Token — xem doc #2 mục C)

3) Trích danh tính -> AuthenticatedUser:
     sub, email, email_verified, name, picture
```

Vì sao mỗi kiểm tra đều cần thiết:

| Kiểm tra | Chặn điều gì |
|---|---|
| Chữ ký RS256 bằng public key Google (JWKS) | Token giả mạo / bị sửa nội dung |
| `iss` | Token do một issuer khác phát ra |
| `aud == client_id` | Token vốn cấp cho **app khác** bị đem dùng lại ở app mình |
| `exp` / `iat` | Token đã hết hạn hoặc thời gian bất thường |
| `nonce == expectedNonce` | **Replay** một ID Token cũ vào phiên login hiện tại |

Kết quả trả về là record `AuthenticatedUser` — chính là "kết quả đăng nhập":

```java
public record AuthenticatedUser(
        String sub,           // subject: ID ổn định, duy nhất của user tại Google
        String email,
        boolean emailVerified,
        String name,
        String picture
) {}
```

> Chi tiết cơ chế JWKS (lấy & cache public key theo `kid`) nằm ở service `GoogleJwksClientService` — được `IdTokenVerifierService` gọi qua `jwksClientService.resolve(kid)`.

### Bước 6 — Lưu user + token + tính thời điểm hết hạn

```java
session.setAttribute(SESSION_USER, user);
session.setAttribute(SESSION_TOKEN, token);

Instant expiresAt = Instant.now().plusSeconds(token.expires_in());
session.setAttribute(SESSION_EXPIRES_AT, expiresAt);
```

- `SESSION_USER` (`oidc_user`): danh tính đã verify — dùng để hiển thị `/profile`.
- `SESSION_TOKEN` (`oidc_token`): cả object `TokenResponse` (chứa access + refresh token).
- `SESSION_EXPIRES_AT` (`oidc_expires_at`): mốc thời gian tuyệt đối access token hết hạn = *bây giờ + expires_in*. Dùng ở doc #5 để biết khi nào cần refresh.

### Bước 7 — Dọn `state`, `nonce`, `code_verifier` (dùng một lần)

```java
session.removeAttribute(SESSION_STATE);
session.removeAttribute(SESSION_NONCE);
session.removeAttribute(SESSION_CODE_VERIFIER);
```

Cả ba giá trị chỉ có ý nghĩa cho **một** lần authorize↔callback. Xong việc thì xoá đi, tránh tái sử dụng.

### Bước 8 — Hiển thị kết quả

```java
model.addAttribute("hasAccessToken", token.access_token() != null);
model.addAttribute("hasRefreshToken", token.refresh_token() != null);
model.addAttribute("expiresIn", token.expires_in());
model.addAttribute("scope", token.scope());
model.addAttribute("tokenType", token.token_type());
return "connected";
```

Trang `connected.html` hiển thị các thông tin token để **quan sát** (có access token chưa, có refresh token chưa, còn sống bao lâu, scope nào được cấp).

## Ai giữ gì sau bước này?

```
   SERVER (session của user)
   ┌────────────────────────────────────────────────┐
   │ oidc_user        = AuthenticatedUser{           │  <- danh tính đã verify (/profile)
   │        sub, email, name, picture ... }           │
   │ oidc_token       = TokenResponse{                │
   │        access_token  = "ya29...."                 │  <- gọi Calendar API
   │        refresh_token = "1//0g..."                 │  <- xin access token mới
   │        id_token      = "<JWT đã verify>"          │
   │        expires_in    = 3599  }                    │
   │ oidc_expires_at  = <now + 3599s>                  │
   │ (oidc_state, oidc_nonce, oidc_code_verifier XOÁ)  │
   └────────────────────────────────────────────────┘
```

Trình duyệt **không** giữ token — nó chỉ có cookie `JSESSIONID`. Mọi truy cập token về sau đều tra qua session (xem doc #1).

## Vì sao đổi token phải làm ở backend (server-to-server)?

```
   Cách AN TOÀN (dự án dùng):                 Cách KHÔNG an toàn:
   Browser chỉ mang code về backend           Browser tự gọi token endpoint
   Backend đổi code + client_secret           -> phải nhúng client_secret vào JS
        (secret nằm kín ở server)                -> lộ secret cho mọi người!
```

`client_secret` là bí mật của ứng dụng, **chỉ được nằm ở server**. Vì thế bước đổi token luôn thực hiện phía backend qua kênh HTTPS kín, không bao giờ để trình duyệt làm.

## Các lỗi thường gặp ở bước này (đã gặp khi làm dự án)

| Lỗi trả về | Nguyên nhân |
|---|---|
| `invalid_grant: Missing code verifier` | `code_verifier` trong session bị `null` (session mất) hoặc form thiếu/sai key `code_verifier` |
| `invalid_grant` (code đã dùng) | Dùng lại `code` cũ (F5 trang callback) — code chỉ dùng **một lần** |
| `redirect_uri_mismatch` | `redirect_uri` lúc đổi token khác lúc authorize / chưa đăng ký trên Google Console |
| `invalid_client` | Sai/thiếu `client_secret` |
| `Khong nhan duoc id_token tu Google` | `scope` thiếu `openid` → Google không phát ID Token |
| `ID token khong hop le: nonce khong khop...` | `nonce` trong ID Token khác `oidc_nonce` trong session → nghi ngờ replay |
| `ID token khong hop le: aud khong khop...` | ID Token cấp cho client_id khác |

## Tóm tắt

1. Google redirect về `/oidc/callback` với `code` + `state` (hoặc `error`).
2. Nếu có `error` → trang lỗi. Verify `state` khớp session → chống CSRF.
3. Lấy `code_verifier` (PKCE) + `expectedNonce` từ session; gọi **token endpoint server-to-server** để đổi `code` lấy token.
4. Bắt buộc có `id_token`; **verify ID Token** (chữ ký JWKS + `iss`/`aud`/`exp`/`iat` + `nonce`) → ra `AuthenticatedUser`.
5. Lưu `user` + `TokenResponse` + `expiresAt` vào session; xoá `state`/`nonce`/`code_verifier` (dùng một lần).
6. Render `connected.html`. Từ đây app đã đăng nhập xong và có access token để gọi Calendar API (doc #4).
