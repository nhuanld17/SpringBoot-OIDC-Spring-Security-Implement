# Verify ID Token — JWKS + Chữ ký RS256 (đào sâu Bước 5 của Callback)

Doc này giải thích chi tiết **"trái tim" của OIDC**: làm sao backend **tự tay** verify một `id_token` mà không dùng thư viện OAuth có sẵn. Đây chính là **Bước 5** trong luồng callback (doc #3) — được tách riêng vì cơ chế bên trong khá dày.

Các thành phần tham gia:

```
OidcAuthController.callback()
        │  idTokenVerifierService.verify(idToken, expectedNonce)
        ▼
IdTokenVerifierService  ──────────────┬──────────────▶  JwtUtil        (tách JWT, base64url-decode, parse JSON)
        │                             └──────────────▶  GoogleJwksClientService.resolve(kid)
        │                                                       │  (cache theo kid; miss -> refetch JWKS)
        ▼                                                       ▼
   AuthenticatedUser                                    Google JWKS endpoint
                                                     https://www.googleapis.com/oauth2/v3/certs
```

---

## 0. ID Token là gì? Vì sao phải verify?

`id_token` là một **JWT** (JSON Web Token) do Google phát ra, dạng 3 phần ngăn bởi dấu chấm:

```
   header . payload . signature
   ┌────┐   ┌─────┐   ┌───────┐
   base64url mỗi phần

header  = { "alg": "RS256", "kid": "abc123", "typ": "JWT" }
payload = { "iss": "...", "aud": "<client_id>", "sub": "...", "email": "...",
            "nonce": "...", "exp": ..., "iat": ... }        <-- gọi là "claims"
signature = ký RSA lên chuỗi  base64url(header) + "." + base64url(payload)
```

Payload chỉ là base64url — **ai cũng đọc/sửa được**. Thứ khiến ID Token đáng tin là **chữ ký** ở phần 3: chỉ Google (giữ private key) mới ký được. Nếu ai đó sửa payload, chữ ký sẽ không còn khớp.

> ⚠️ Do đó **tuyệt đối không tin claims cho tới khi verify xong chữ ký**. Đọc `email` từ một token chưa verify là lỗ hổng bảo mật.

---

## 1. RS256 & vì sao dùng JWKS (bất đối xứng)

`alg = RS256` nghĩa là: **RSA + SHA-256**, một thuật toán ký **bất đối xứng**:

```
   Google  ──ký bằng PRIVATE key (bí mật, chỉ Google có)──▶  signature
   App     ──verify bằng PUBLIC key (công khai)──────────▶  đúng/sai
```

- App **không cần** biết private key. Nó chỉ cần **public key** của Google để kiểm chữ ký.
- Public key được Google publish công khai tại **JWKS endpoint** (`jwks-uri` = `https://www.googleapis.com/oauth2/v3/certs`).
- **JWKS** = *JSON Web Key Set* — một danh sách các public key, mỗi key có một `kid` (key id).

Vì sao có nhiều key và có `kid`? Vì **Google xoay (rotate) key định kỳ**. Tại một thời điểm có vài key song song. Header của ID Token ghi `kid` để nói "token này ký bằng key nào" → app tra đúng key đó trong JWKS.

## 2. Các tiện ích JWT "thô" — `JwtUtil`

`JwtUtil` chỉ làm phần **cơ học**, **không** verify (verify nằm ở `IdTokenVerifierService`):

```java
// Tách "header.payload.signature" -> 3 phần
public static String[] split(String jwt) {
    String[] parts = jwt.split("\\.");
    if (parts.length != 3) {
        throw new IllegalArgumentException("ID token khong dung dinh dang JWT (can 3 phan).");
    }
    return parts;
}

// base64url-decode -> bytes thô
public static byte[] base64UrlDecode(String data) {
    return Base64.getUrlDecoder().decode(data);
}

// Decode 1 phần (header/payload) -> cây JSON để đọc claim
public static JsonNode decodeToJson(String part) {
    byte[] json = base64UrlDecode(part);
    return new ObjectMapper().readTree(new String(json, StandardCharsets.UTF_8));
}
```

> Lưu ý dùng **base64url** (`Base64.getUrlDecoder()`), không phải base64 thường: JWT thay `+`/`/` bằng `-`/`_` và bỏ padding `=` để an toàn trên URL.

## 3. Luồng verify đầy đủ — `IdTokenVerifierService.verify(idToken, expectedNonce)`

```java
public AuthenticatedUser verify(String idToken, String expectedNonce) {
    String[] parts = JwtUtil.split(idToken);
    String headerB64 = parts[0], payloadB64 = parts[1], signatureB64 = parts[2];

    JsonNode header = JwtUtil.decodeToJson(headerB64);
    JsonNode claims = JwtUtil.decodeToJson(payloadB64);

    // 1) Thuật toán + chữ ký ------------------------------------------
    if (!"RS256".equals(text(header, "alg")))
        throw new IllegalStateException("alg khong phai RS256: ...");
    String kid = text(header, "kid");
    if (kid == null) throw new IllegalStateException("Header ID token thieu 'kid'.");

    RSAPublicKey publicKey = jwksClientService.resolve(kid);          // <-- tra public key theo kid
    String signingInput = headerB64 + "." + payloadB64;              // đúng phần được ký
    if (!verifySignature(signingInput, signatureB64, publicKey))
        throw new IllegalStateException("Chu ky ID token khong hop le (co the bi gia mao).");

    // 2) Claims -------------------------------------------------------
    String iss = text(claims, "iss");
    if (iss == null || !VALID_ISSUERS.contains(iss))
        throw new IllegalStateException("iss khong hop le: " + iss);

    String aud = text(claims, "aud");
    if (aud == null || !aud.equals(props.clientId()))
        throw new IllegalStateException("aud khong khop client_id cua ung dung.");

    long now = Instant.now().getEpochSecond();
    if (claims.path("exp").asLong(0) + CLOCK_SKEW_SECONDS < now)
        throw new IllegalStateException("ID token da het han.");
    if (claims.path("iat").asLong(0) - CLOCK_SKEW_SECONDS > now)
        throw new IllegalStateException("ID token co iat trong tuong lai.");

    String nonce = text(claims, "nonce");
    if (nonce == null || !nonce.equals(expectedNonce))
        throw new IllegalStateException("nonce khong khop -> nghi ngo replay. Tu choi.");

    // 3) Trích danh tính ---------------------------------------------
    return new AuthenticatedUser(
            text(claims, "sub"), text(claims, "email"),
            claims.path("email_verified").asBoolean(false),
            text(claims, "name"), text(claims, "picture"));
}
```

### 3a. Kiểm tra chữ ký (phần lõi)

```java
private boolean verifySignature(String signingInput, String signatureB64, RSAPublicKey key) {
    Signature sig = Signature.getInstance("SHA256withRSA");   // "SHA256withRSA" == RS256
    sig.initVerify(key);
    sig.update(signingInput.getBytes(StandardCharsets.US_ASCII));  // header.payload
    return sig.verify(JwtUtil.base64UrlDecode(signatureB64));      // so với signature
}
```

Cơ chế:

```
signingInput = base64url(header) + "." + base64url(payload)
                                │
       Google ký (private key)  │  ───────▶  signature (phần 3 của JWT)
                                │
       App verify (public key)  │  ───────▶  sig.verify(signingInput, signature) == true?
                                ▼
        - Nếu payload bị sửa 1 ký tự -> signingInput đổi -> verify FALSE
        - Nếu ký bằng key khác        -> verify FALSE
```

Điểm tinh tế: phần được ký là **chuỗi base64url gốc** `header.payload` (không phải JSON đã decode). Vì thế ta ghép lại `headerB64 + "." + payloadB64` y hệt chuỗi Google đã ký.

### 3b. Bảng claims và ý nghĩa

| Claim | Kiểm tra | Chặn điều gì |
|-------|----------|--------------|
| `iss` | ∈ `{https://accounts.google.com, accounts.google.com}` | Token do issuer khác phát |
| `aud` | `== client_id` của app | Token vốn cấp cho **app khác** bị dùng lại |
| `exp` | `exp + 60s ≥ now` | Token đã hết hạn |
| `iat` | `iat - 60s ≤ now` | Token có thời điểm phát ở tương lai (bất thường) |
| `nonce` | `== expectedNonce` (lấy từ `oidc_nonce` trong session) | **Replay** ID Token cũ (xem doc #2 mục C) |

`CLOCK_SKEW_SECONDS = 60` là **leeway** bù chênh lệch đồng hồ giữa server và Google (giống vùng 60s ở refresh — doc #5).

`VALID_ISSUERS` chấp nhận **cả hai** dạng `https://accounts.google.com` và `accounts.google.com` vì Google phát hành ID Token với một trong hai giá trị này.

## 4. Lấy & cache public key — `GoogleJwksClientService`

```java
private volatile Map<String, RSAPublicKey> cache = new HashMap<>();

/** Trả public key theo kid; miss thì tải lại JWKS 1 lần. */
public RSAPublicKey resolve(String kid) {
    RSAPublicKey key = cache.get(kid);
    if (key != null) return key;      // hit cache

    refresh();                        // miss -> có thể Google vừa xoay key
    key = cache.get(kid);
    if (key == null)
        throw new IllegalStateException("Khong tim thay public key (kid=" + kid + ") trong JWKS Google.");
    return key;
}

private void refresh() {
    Jwks jwks = restClient.get().uri(props.jwksUri()).retrieve().body(Jwks.class);
    Map<String, RSAPublicKey> fresh = new HashMap<>();
    if (jwks != null && jwks.keys() != null)
        for (Jwks.Jwk jwk : jwks.keys())
            fresh.put(jwk.kid(), toRsaPublicKey(jwk));
    this.cache = fresh;               // thay nguyên map (volatile) -> thread-safe kiểu copy-on-write
}
```

Chiến lược cache **lazy + refetch-on-miss**:

```
resolve(kid):
    ┌── cache có kid?  ── CÓ ──▶ trả key luôn (không gọi mạng)
    │
    └── KHÔNG ──▶ refresh() (GET JWKS 1 lần)
                     ├── giờ có kid  ──▶ trả key
                     └── vẫn không   ──▶ ném lỗi (kid lạ thật sự)
```

Vì sao thiết kế vậy: **Google xoay key định kỳ**. Bình thường `kid` nằm sẵn trong cache → verify không tốn request mạng. Khi Google vừa xoay sang key mới (gặp `kid` lạ), ta refetch **đúng một lần** để nạp key mới. Trường hợp bình thường gần như luôn hit cache.

> `cache` khai báo `volatile` và `refresh()` **thay nguyên map mới** (không sửa map cũ tại chỗ) → an toàn khi nhiều request đọc đồng thời (copy-on-write đơn giản).

### 4a. Dựng `RSAPublicKey` từ `(n, e)`

JWKS không trả key ở dạng PEM/X.509, mà ở dạng hai số **modulus `n`** và **exponent `e`** (base64url). Ta tự dựng `RSAPublicKey`:

```java
private RSAPublicKey toRsaPublicKey(Jwks.Jwk jwk) {
    BigInteger modulus  = new BigInteger(1, JwtUtil.base64UrlDecode(jwk.n())); // "1" = dấu dương
    BigInteger exponent = new BigInteger(1, JwtUtil.base64UrlDecode(jwk.e()));
    KeyFactory factory  = KeyFactory.getInstance("RSA");
    return (RSAPublicKey) factory.generatePublic(new RSAPublicKeySpec(modulus, exponent));
}
```

> `new BigInteger(1, bytes)` — tham số `1` ép dấu **dương**. Nếu byte đầu ≥ 0x80, constructor `BigInteger(byte[])` thường sẽ hiểu nhầm thành số âm; `n` và `e` của RSA luôn là số nguyên dương lớn nên phải truyền signum = 1.

### 4b. Cấu trúc `Jwks` (record)

```java
public record Jwks(List<Jwk> keys) {
    public record Jwk(
            String kid,  // key id - khớp "kid" trong header ID token
            String kty,  // key type = "RSA"
            String alg,  // "RS256"
            String use,  // "sig" (dùng để verify chữ ký)
            String n,    // modulus  (base64url)
            String e     // exponent (base64url)
    ) {}
}
```

Vì Jackson cấu hình `FAIL_ON_UNKNOWN_PROPERTIES=false`, các field thừa Google trả về (nếu có) sẽ bị bỏ qua, không gây lỗi parse.

## 5. Toàn cảnh một lần verify

```
idToken = "eyJhbGci...header . eyJpc3Mi...payload . SIG"
   │
   │ JwtUtil.split(...)              -> [headerB64, payloadB64, signatureB64]
   │ JwtUtil.decodeToJson(header)    -> { alg:"RS256", kid:"abc" }
   ▼
alg == RS256?  kid != null?
   │
   │ jwksClientService.resolve("abc")
   │      ├── cache hit  -> RSAPublicKey
   │      └── miss       -> GET https://www.googleapis.com/oauth2/v3/certs -> dựng key -> cache
   ▼
verifySignature(headerB64 + "." + payloadB64, signatureB64, publicKey)  == true?
   │
   ▼
claims: iss ✓  aud==client_id ✓  exp/iat (±60s) ✓  nonce==oidc_nonce ✓
   │
   ▼
AuthenticatedUser{ sub, email, emailVerified, name, picture }   <-- "kết quả đăng nhập"
```

Bất kỳ bước nào sai → ném `IllegalStateException`, `OidcAuthController.callback()` bắt (`catch RuntimeException`) và hiển thị `error-page` (xem doc #3).

## 6. Vì sao dự án tự verify thay vì dùng thư viện?

Đây là project **học** cơ chế OIDC "chay tay". Trong thực tế sản phẩm, người ta thường dùng thư viện (`nimbus-jose-jwt`, Spring Security OAuth2 Resource Server...) để:
- Tự động cache & xoay JWKS theo header `Cache-Control`.
- Chống các tấn công tinh vi (ví dụ `alg=none`, nhầm lẫn thuật toán HS/RS).

Ở đây ta **cố tình làm thủ công** để thấy rõ từng mảnh: tách JWT → tra JWKS theo `kid` → dựng `RSAPublicKey` từ `(n, e)` → verify `SHA256withRSA` → kiểm claims. Dự án đã chốt cứng `alg` phải là `RS256` (loại bỏ `alg=none` và HS256), là biện pháp phòng thủ tối thiểu quan trọng.

## Tóm tắt

1. ID Token là JWT `header.payload.signature`; **chỉ tin sau khi verify chữ ký**.
2. RS256 là ký bất đối xứng: Google ký bằng private key, app verify bằng **public key** lấy từ **JWKS** (`jwks-uri`).
3. `IdTokenVerifierService`: check `alg=RS256` + `kid` → `resolve(kid)` lấy public key → `verifySignature` → kiểm `iss`/`aud`/`exp`/`iat`/`nonce`.
4. `GoogleJwksClientService`: cache public key theo `kid` (lazy, refetch-on-miss vì Google xoay key), dựng `RSAPublicKey` từ `(n, e)` base64url.
5. Verify thành công → `AuthenticatedUser`; sai bất kỳ điều gì → exception → `error-page`.
