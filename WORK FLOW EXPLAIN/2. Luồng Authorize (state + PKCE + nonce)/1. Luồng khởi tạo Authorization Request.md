# Luồng Authorize — Khởi tạo Authorization Request

Đây là **bước mở màn** của luồng OIDC: đăng nhập (xác thực danh tính) kết hợp ủy quyền đọc Google Calendar. Mục tiêu: chuẩn bị các tham số an toàn (`state`, `PKCE`, và `nonce`) rồi **redirect** trình duyệt sang trang đăng nhập/consent của Google.

Endpoint phụ trách: `GET /oidc/authorize` trong `OidcAuthController`.

---

## Vị trí trong toàn bộ flow

```
[/oidc/authorize]     <-- doc nay mo ta buoc nay
        │
        ▼
   Google consent & login
        │
        ▼
[/oidc/callback]      <-- doc #3 (verify state, doi code, verify ID token, nhan tokens)
        │
        ▼
   Calendar API        <-- doc #4 (goi API bang access token)
```

Trong bước này **chưa có token nào cả**. Ta mới chỉ bắt đầu luồng đăng nhập — nói với Google: "tôi là client X, muốn **xác thực danh tính** người dùng (OIDC) kèm theo xin quyền **đọc lịch** (Calendar), hãy hỏi người dùng và gửi authorization code về đúng địa chỉ Z".

Vì đây là OIDC (không phải OAuth2 thuần), `scope` có chứa `openid` → Google sẽ trả về thêm một **ID Token** (JWT chứa danh tính người dùng) ở bước callback, bên cạnh access token / refresh token.

---

## Toàn cảnh sơ đồ

```
Browser
   │
   │  GET /oidc/authorize
   ▼
OidcAuthController.authorize()
   │
   ├── 1. Sinh state ngẫu nhiên                      (chống CSRF)
   ├── 2. Sinh nonce ngẫu nhiên                      (chống replay ID Token)
   ├── 3. Sinh code_verifier + code_challenge (S256)  (PKCE)
   │
   ├── 4. Lưu vào HttpSession (phía server):
   │        oidc_state         = state
   │        oidc_nonce         = nonce
   │        oidc_code_verifier = code_verifier
   │
   ├── 5. Build URL authorize, gửi kèm:
   │        client_id, redirect_uri, response_type=code,
   │        scope (openid profile email + calendar),
   │        state, nonce, code_challenge, code_challenge_method=S256,
   │        access_type=offline, prompt=consent
   │
   └── 6. HTTP 302 Redirect
   ▼
https://accounts.google.com/o/oauth2/v2/auth?...
   │
   │  Người dùng đăng nhập + bấm "Allow"
   ▼
Google redirect về /oidc/callback?code=...&state=...
```

Điểm mấu chốt cần nhớ ngay: **`code_verifier`, `state` và `nonce` được giữ lại trong session ở server, KHÔNG gửi trực tiếp giá trị `code_verifier` đi.** Google nhận `state`, `nonce`, và `code_challenge` (bản băm). Đây là nền tảng của toàn bộ tính an toàn.

---

## Chi tiết từng bước (kèm code trong dự án)

### Bước 1, 2 & 3 — Sinh các tham số an toàn

```java
// OidcAuthController.authorize()
String state         = PkceUtil.generateState();
String nonce         = NonceUtils.generateNonce();
String codeVerifier  = PkceUtil.generateCodeVerifier();
String codeChallenge = PkceUtil.generateCodeChallenge(codeVerifier);
```

Cả 3 nhóm giá trị đều sinh ngẫu nhiên bảo mật bằng `SecureRandom`.

*   **state**: Chuỗi ngẫu nhiên dùng chống CSRF (buộc callback vào đúng phiên đã khởi tạo).
*   **nonce**: Chuỗi ngẫu nhiên nhúng vào **ID Token**, dùng chống replay ID Token (đặc trưng OIDC).
*   **PKCE (code_verifier / code_challenge)**: Cặp mã bảo mật chống đánh cắp authorization code.

Xem cấu trúc biến đổi của PKCE:
```
code_verifier  =  "aoTBnDw1N66Cl..."          (bí mật, giữ ở server)
                        │
                        │  SHA-256  +  Base64URL
                        ▼
code_challenge =  "HmhhUzBTdkNa..."            (công khai, gửi cho Google)
```

### Bước 4 — Lưu các giá trị vào session

```java
session.setAttribute(SESSION_STATE, state);
session.setAttribute(SESSION_NONCE, nonce);
session.setAttribute(SESSION_CODE_VERIFIER, codeVerifier);
```

Với các keys (khai báo trong `OidcAuthController`, tiền tố `oidc_` để **tách khỏi** nhánh Calendar dùng `oauth_*`):
```java
public static final String SESSION_STATE         = "oidc_state";
public static final String SESSION_NONCE         = "oidc_nonce";
public static final String SESSION_CODE_VERIFIER = "oidc_code_verifier";
```

Vì sao phải lưu?
- `state`: để bước callback **so lại** — nếu state trả về không khớp thì đây là request giả mạo/CSRF.
- `nonce`: để bước callback **so lại** với claim `nonce` bên trong ID Token — chống việc tái sử dụng một ID Token cũ.
- `code_verifier`: để bước callback dùng nó **chứng minh** với Google rằng chính client này đã khởi tạo request (PKCE).

Nhờ cơ chế session (xem doc #1), mỗi trình duyệt có `oidc_state` / `oidc_nonce` / `oidc_code_verifier` **riêng**, không lẫn giữa những người dùng khác nhau.

### Bước 5 — Build Authorization Request URL

```java
String authorizeUrl = UriComponentsBuilder
        .fromUriString(props.authorizationUri())   // https://accounts.google.com/o/oauth2/v2/auth
        .queryParam("client_id", props.clientId())
        .queryParam("redirect_uri", props.redirectUri())
        .queryParam("response_type", "code")           // xin authorization CODE
        .queryParam("scope", props.scope())            // openid profile email + calendar.readonly
        .queryParam("state", state)                    // chống CSRF
        .queryParam("nonce", nonce)                    // chống replay ID Token
        .queryParam("code_challenge", codeChallenge)   // PKCE (chỉ gửi challenge)
        .queryParam("code_challenge_method", "S256")
        .queryParam("access_type", "offline")          // xin cả REFRESH token
        .queryParam("prompt", "consent")               // luôn hiện consent -> chắc chắn có refresh token
        .build()
        .encode()   // encode đúng cách (scope có ':' và '/')
        .toUriString();
```

Ý nghĩa từng tham số:

| Tham số | Vai trò |
|---------|---------|
| `client_id` | App nào đang xin quyền |
| `redirect_uri` | Google **chỉ** trả code về đúng URI đã đăng ký trước (`/oidc/callback`) → chống chiếm đoạt code |
| `response_type=code` | Chọn luồng Authorization Code (không lấy token trực tiếp trên URL) |
| `scope` | Xin quyền gì — ở đây `openid profile email` (OIDC danh tính) + `calendar.readonly` (đọc lịch) |
| `state` | Chuỗi ngẫu nhiên; callback phải trả đúng chuỗi này → chống CSRF |
| `nonce` | Chuỗi ngẫu nhiên; sẽ được Google **nhúng vào ID Token** → chống replay ID Token |
| `code_challenge` + `code_challenge_method=S256` | Bản băm của `code_verifier` → PKCE |
| `access_type=offline` | Cho phép cấp **refresh token** |
| `prompt=consent` | Ép hiện lại màn consent để chắc chắn nhận refresh token |

> `.encode()` là bắt buộc: `scope` chứa khoảng trắng, `:` và `/` (ví dụ `openid profile email https://www.googleapis.com/auth/calendar.readonly`), phải được encode đúng khi đưa vào query string.

### Bước 6 — Redirect sang Google

```java
return "redirect:" + authorizeUrl;
```

Spring trả về **HTTP 302** kèm header `Location: https://accounts.google.com/...`. Trình duyệt tự động đi tới trang consent của Google.

## Ai giữ gì sau bước này?

```
   SERVER (session)                                   GOOGLE nhận được (trên URL)
   ┌──────────────────────────────┐                  ┌───────────────────────────────┐
   │ oidc_state         = S        │  ──── state ───▶ │ state          = S            │
   │ oidc_nonce         = N        │  ──── nonce ───▶ │ nonce          = N            │
   │ oidc_code_verifier = V        │                 │ code_challenge = SHA256(V)     │
   └──────────────────────────────┘   ─ challenge ──▶ │ client_id, scope, ...          │
        (V KHÔNG bao giờ rời server)                  └───────────────────────────────┘
```

- Server giữ **bí mật** `code_verifier (V)` trong session; `state` và `nonce` cũng lưu server để đối chiếu ở callback.
- Google chỉ thấy `code_challenge` (= băm của V), `state` và `nonce`.
- `nonce` sẽ quay lại ta **nằm bên trong ID Token** (JWT), không phải trên query string của callback.

---

## Ba lớp bảo vệ khác nhau (không thay thế nhau)

`state`, `PKCE` và `nonce` giải quyết **ba vấn đề khác nhau**. Dưới đây là cơ chế chi tiết của từng cái.

---

### A. `state` chống CSRF ở bước callback như thế nào?

**CSRF trong OAuth (authorization code injection) là gì?**

Callback `/oidc/callback?code=...` chỉ là một request GET bình thường. Nếu **không có gì ràng buộc**, thì bất kỳ ai cũng có thể lừa trình duyệt nạn nhân gọi callback với **một authorization code do kẻ tấn công chuẩn bị sẵn**.

Kịch bản tấn công khi KHÔNG có `state`:

```
1. Kẻ tấn công tự bấm "Connect" bằng tài khoản Google CỦA HẮN
   -> Google cấp cho hắn 1 authorization code:  code_ATTACKER
   -> Nhưng hắn KHÔNG dùng code này để hoàn tất

2. Hắn nhúng vào web/email 1 link (hoặc ảnh tự động load):
      http://localhost:8080/oidc/callback?code=code_ATTACKER

3. Nạn nhân (đang đăng nhập app) vô tình mở link đó
   -> Trình duyệt nạn nhân gọi callback với code_ATTACKER
   -> App đổi code_ATTACKER lấy token -> lưu vào SESSION CỦA NẠN NHÂN

4. Hậu quả: session của nạn nhân giờ gắn với tài khoản Google của kẻ tấn công.
   Nạn nhân tưởng đang thao tác trên tài khoản mình, nhưng thực chất
   mọi dữ liệu đổ vào tài khoản kẻ tấn công.
```

**`state` chặn điều này ra sao?**

Ở bước authorize, ta sinh `state` ngẫu nhiên và **gắn nó vào session của nạn nhân**:

```java
// authorize()
String state = PkceUtil.generateState();
session.setAttribute(SESSION_STATE, state);   // state buộc chặt vào session người khởi tạo
// ... state cũng được gửi lên Google qua query param
```

Ở bước callback, ta **so lại**:

```java
// callback()
String savedState = (String) session.getAttribute(SESSION_STATE);
if (savedState == null || !savedState.equals(state)) {
    model.addAttribute("error", "State khong khop -> nghi ngo CSRF. Tu choi.");
    return "error-page";
}
```

Vì sao kẻ tấn công thua:

```
Session nạn nhân giữ:   oidc_state = S_victim   (ngẫu nhiên, kẻ tấn công KHÔNG biết)

Link giả của kẻ tấn công:  /oidc/callback?code=code_ATTACKER&state=???
                                                                     │
                     kẻ tấn công không đoán được S_victim ───────────┘

callback so:  state trên URL  ==  oidc_state trong session ?
              ──────────────────────────────────────────────
                        KHÔNG KHỚP  ->  từ chối
```

- `state` sinh từ `SecureRandom`, **khác nhau cho mỗi phiên**, và **lưu phía server** → kẻ tấn công không thể biết `S_victim` để nhét vào link giả.
- Google, khi redirect thật, **trả lại đúng** `state` mà app đã gửi đi. Nên callback hợp lệ luôn khớp; callback giả mạo thì không.

> Bản chất: `state` **buộc chặt callback vào đúng phiên đã khởi tạo authorize**. Trả lời câu hỏi *"cái callback này có thực sự do chính người dùng này bắt đầu không?"*.

---

### B. `PKCE` chống đánh cắp authorization code như thế nào?

**Authorization code bị đánh cắp bằng cách nào?**

`code` được Google trả về **trên URL** của callback:

```
http://localhost:8080/oidc/callback?code=4/0AeanS0b...&state=...
```

URL thì dễ rò rỉ qua nhiều đường: lịch sử trình duyệt, log server/proxy, header `Referer`, hoặc app độc hại trên mobile "cướp" redirect.

Nếu **không có PKCE**, kẻ tấn công cướp được `code` có thể tự gọi token endpoint để đổi lấy token:

```
POST /token
   grant_type=authorization_code
   code=<code đánh cắp được>
   redirect_uri=...
   client_id=...
-> LẤY ĐƯỢC access token   (nguy hiểm!)
```

**PKCE chặn điều này ra sao?**

Nhớ lại: ở bước authorize, ta chỉ gửi cho Google **`code_challenge`** (= băm SHA-256 của `code_verifier`), còn **`code_verifier` giữ bí mật trong session**:

```java
// authorize()
String codeVerifier  = PkceUtil.generateCodeVerifier();              // bí mật, lưu session
String codeChallenge = PkceUtil.generateCodeChallenge(codeVerifier); // gửi cho Google
session.setAttribute(SESSION_CODE_VERIFIER, codeVerifier);
// URL gửi Google: ...&code_challenge=<challenge>&code_challenge_method=S256
```

Google **ghi nhớ** `code_challenge` gắn với `code` mà nó phát ra. Đến bước đổi token (doc #3), token endpoint **bắt buộc** kèm `code_verifier` gốc:

```java
// GoogleOidcService.exchangeCodeForToken(code, codeVerifier)
form.add("grant_type", "authorization_code");
form.add("code", code);
form.add("code_verifier", codeVerifier);   // <-- xuất trình bí mật gốc
```

Google tự tính `SHA-256(code_verifier)` và so với `code_challenge` đã lưu:

```
Lúc authorize:   Google lưu   challenge = SHA256(V)
Lúc đổi token:   client gửi   code + code_verifier = V'
                 Google kiểm:  SHA256(V')  ==  challenge ?

   Client thật:      V' = V   ->  SHA256(V) == SHA256(V)   ->  OK, cấp token
   Kẻ tấn công:      chỉ có code, KHÔNG có V
                     đoán V từ challenge? -> bất khả thi (SHA-256 một chiều)
                     -> thiếu code_verifier -> Google từ chối (invalid_grant)
```

Vì sao kẻ tấn công thua:
- Thứ đi kèm token request là `code_verifier` (bí mật), **không phải** `code_challenge` (thứ có thể lộ trên URL authorize).
- Từ `code_challenge` **không suy ngược** ra `code_verifier` được (SHA-256 là hàm một chiều).
- `code_verifier` **chỉ tồn tại trong session của client hợp lệ**, không bao giờ xuất hiện trên đường truyền tới khi đổi token (bước đổi token là server-to-server, kín).

> Bản chất: PKCE **buộc chặt authorization code vào đúng client đã tạo ra nó**. Có `code` mà không có `code_verifier` thì `code` trở nên vô dụng.

> Ghi chú: dự án là web app *confidential* (có `client_secret`), bản thân secret đã là một lớp bảo vệ. Nhưng theo OAuth 2.1, PKCE được khuyến nghị cho **mọi** client như một lớp phòng thủ theo chiều sâu — nên ta vẫn dùng.

### C. `nonce` chống replay ID Token như thế nào? (đặc trưng OIDC)

Đây là lớp bảo vệ **chỉ có ở OIDC**, vì chỉ OIDC mới trả về **ID Token** (một JWT chứa danh tính người dùng: `sub`, `email`, `name`...). `state` và `PKCE` bảo vệ *authorization code*; còn `nonce` bảo vệ *chính ID Token*.

**Replay ID Token là gì?**

ID Token là một JWT có chữ ký hợp lệ của Google. Nếu một kẻ tấn công **bắt lại được một ID Token cũ** (đã từng phát hành hợp lệ, còn trong hạn), hắn có thể thử "tráo" nó vào một luồng đăng nhập khác để giả danh người dùng đó. Vì chữ ký vẫn đúng, nếu app **chỉ kiểm tra chữ ký** thì sẽ bị lừa.

**`nonce` chặn điều này ra sao?**

```
1. authorize(): sinh nonce = N (ngẫu nhiên), lưu session + gửi lên Google
2. Google nhúng N vào claim "nonce" BÊN TRONG ID Token rồi ký
3. callback(): sau khi verify chữ ký, app so claim nonce với N đã lưu trong session
```

Trong dự án, `nonce` được lưu ở authorize và lấy ra ở callback để đưa cho verifier:

```java
// callback()
String expectedNonce = (String) session.getAttribute(SESSION_NONCE);
...
AuthenticatedUser user = idTokenVerifierService.verify(token.id_token(), expectedNonce);
```

`IdTokenVerifierService.verify(...)` kiểm tra: chữ ký (bằng JWKS của Google), `iss`, `aud`, `exp`, **và** `nonce` khớp `expectedNonce`.

Vì sao kẻ tấn công thua:

```
ID Token cũ (bắt lại được) chứa:   nonce = N_old   (đã ký cứng, không sửa được vì sẽ hỏng chữ ký)
Session của luồng login mới giữ:   oidc_nonce = N_new  (ngẫu nhiên, khác N_old)

verify so:  nonce trong ID Token  ==  oidc_nonce trong session ?
            N_old  ==  N_new  ->  KHÔNG KHỚP  ->  từ chối
```

- `nonce` được **ký cứng bên trong** ID Token → kẻ tấn công không thể sửa thành `N_new` mà không phá chữ ký.
- Mỗi luồng login sinh `nonce` mới → một ID Token cũ không bao giờ khớp `nonce` của phiên hiện tại.

> Bản chất: `nonce` **buộc chặt ID Token vào đúng phiên login đã khởi tạo nó**. Trả lời câu hỏi *"cái ID Token này có phải vừa được cấp cho CHÍNH lần đăng nhập này không, hay là bản cũ bị tráo lại?"*.

---

### Tóm tắt sự khác biệt

```
    state  ──►  bảo vệ "ai GỬI callback về"         (chống CSRF / code injection)
    PKCE   ──►  bảo vệ "ai được ĐỔI code lấy token"  (chống đánh cắp code)
    nonce  ──►  bảo vệ "ID Token này có tươi không"  (chống replay ID Token)
```

| | `state` | `PKCE` | `nonce` |
|---|---------|--------|---------|
| Chống | CSRF / code injection | Đánh cắp / tái dùng code | Replay ID Token |
| Ràng buộc vào | đúng **phiên** đã khởi tạo | đúng **client** đã khởi tạo | đúng **lần login** đã khởi tạo |
| Bí mật nằm ở | `oidc_state` trong session | `oidc_code_verifier` trong session | `oidc_nonce` trong session |
| Kiểm tra tại | callback của **app** (so state) | token endpoint của **Google** (so challenge) | callback của **app** (so nonce trong ID Token) |

Ba mục tiêu khác nhau ⇒ **dùng đồng thời cả ba**, không cái nào thay được cái nào.

## Cấu hình liên quan (application.properties)

```properties
google.oidc.client-id=${GOOGLE_CLIENT_ID}
google.oidc.client-secret=${GOOGLE_CLIENT_SECRET}
google.oidc.redirect-uri=http://localhost:8080/oidc/callback
google.oidc.scope=openid profile email https://www.googleapis.com/auth/calendar.readonly
google.oidc.authorization-uri=https://accounts.google.com/o/oauth2/v2/auth
google.oidc.token-uri=https://oauth2.googleapis.com/token
google.oidc.issuer=https://accounts.google.com
google.oidc.jwks-uri=https://www.googleapis.com/oauth2/v3/certs
```

Các giá trị này được nạp vào `GoogleOidcProperties` (record `@ConfigurationProperties(prefix = "google.oidc")`) và inject vào `OidcAuthController` qua biến `props`.

- `issuer` và `jwks-uri` **chưa dùng ở bước này**, nhưng cần cho bước callback: dùng để **verify chữ ký và claim của ID Token** (xem doc #3). `jwks-uri` là nơi lấy public key của Google để kiểm tra chữ ký JWT.

## Tóm tắt

1. `authorize()` sinh `state` + `nonce` + cặp PKCE (`code_verifier` bí mật, `code_challenge` công khai).
2. Lưu `state`, `nonce`, `code_verifier` vào **session server** (mỗi browser một bản riêng, tiền tố `oidc_`).
3. Build URL với đầy đủ tham số an toàn, chỉ gửi `code_challenge` (không gửi `code_verifier`); scope gồm `openid profile email` + `calendar.readonly`.
4. Redirect 302 sang Google để người dùng đăng nhập + consent.
