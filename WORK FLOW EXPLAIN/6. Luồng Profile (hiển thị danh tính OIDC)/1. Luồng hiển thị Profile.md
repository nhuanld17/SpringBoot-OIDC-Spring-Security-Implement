# Luồng Profile — Hiển thị danh tính OIDC

Đây là bước **thu hoạch** của cả luồng OIDC: sau khi đã đăng nhập và verify `id_token` (doc #3), danh tính người dùng (`AuthenticatedUser`) được cất trong session. Trang `/profile` chỉ việc **đọc lại** danh tính đó và hiển thị.

Endpoint phụ trách: `GET /profile` trong `ProfileController`.

Điểm khác biệt so với các doc trước: bước này **không gọi Google, không đụng token**. Nó thuần tuý đọc session — vì "việc khó" (đổi code, verify chữ ký ID Token) đã làm xong ở callback.

---

## Vị trí trong toàn bộ flow

```
[/oidc/callback]  (doc #3)
   │  verify id_token -> AuthenticatedUser
   │  session.setAttribute(oidc_user, user)
   ▼
[/profile]  <-- DOC NÀY   (đọc oidc_user, render)
   │
   ├──▶ /calendars   (doc #4)   — dùng access token
   ├──▶ /oidc/refresh (doc #5)  — refresh token
   └──▶ /logout                 — xoá session
```

`oidc_user` được **ghi** ở đúng một nơi (callback, sau khi verify ID Token) và được **đọc** ở đây. Đó là lý do trang profile tin được dữ liệu: nó đã qua verify đầy đủ trước khi vào session.

---

## Toàn cảnh sơ đồ

```
Browser ──GET /profile──▶ ProfileController.profile()
                                │
   1. user = session.getAttribute(oidc_user)   (AuthenticatedUser)
        └── null?  ->  redirect "/"   (chưa đăng nhập)
                                │
   2. model.addAttribute("user", user)
                                ▼
                        render profile.html  (name, email, sub, picture)
```

---

## Chi tiết từng bước (kèm code trong dự án)

### Toàn bộ controller (rất ngắn)

```java
@Controller
public class ProfileController {

    @GetMapping("/profile")
    public String profile(HttpSession session, Model model) {
        AuthenticatedUser user =
                (AuthenticatedUser) session.getAttribute(OidcAuthController.SESSION_USER);

        // Guard: chưa đăng nhập OIDC -> về trang chủ (giống pattern CalendarController)
        if (user == null) {
            return "redirect:/";
        }

        model.addAttribute("user", user);
        return "profile";
    }
}
```

### Bước 1 — Đọc `oidc_user` từ session (guard null)

```java
AuthenticatedUser user =
        (AuthenticatedUser) session.getAttribute(OidcAuthController.SESSION_USER);
if (user == null) {
    return "redirect:/";
}
```

- `SESSION_USER` = `"oidc_user"` (hằng số khai báo trong `OidcAuthController`).
- Nếu `null` → người dùng chưa đăng nhập OIDC (hoặc session đã hết/logout) → redirect về trang chủ. Đây là **cùng một pattern guard** với `CalendarController` (`accessToken == null -> redirect "/"`).

> Vì sao không cần kiểm tra token còn hạn ở đây? Vì `/profile` **không gọi API Google** — nó chỉ hiển thị thông tin danh tính đã verify. Danh tính (`sub`, `email`, `name`...) không "hết hạn" theo access token; nó tồn tại đến khi session bị xoá.

### Bước 2 — Đẩy `user` ra view

```java
model.addAttribute("user", user);
return "profile";
```

`AuthenticatedUser` là record đã trích từ ID Token đã verify:

```java
public record AuthenticatedUser(
        String sub,           // subject: ID ổn định, duy nhất của user tại Google
        String email,
        boolean emailVerified,
        String name,
        String picture
) {}
```

### `profile.html` hiển thị gì

```html
<h1>👤 Đăng nhập thành công (OIDC)</h1>
<p>Backend đã verify <code>id_token</code> (chữ ký RS256 + claims iss/aud/exp/nonce)
   và xác định bạn là:</p>

<img th:if="${user.picture}" th:src="${user.picture}" .../>
<ul>
    <li>Tên: <b th:text="${user.name}">—</b></li>
    <li>Email: <b th:text="${user.email}">—</b>
        <span th:if="${user.emailVerified}"> (đã xác minh)</span></li>
    <li>Subject (sub): <code th:text="${user.sub}">—</code></li>
</ul>

<a href="/calendars">📅 Xem lịch của tôi</a>
<a href="/oidc/refresh">🔄 Mô phỏng Refresh Token</a>
<a href="/logout">Đăng xuất</a>
```

- `th:if="${user.picture}"` — chỉ hiện avatar nếu có ảnh.
- `emailVerified` — Google cho biết email đã được xác minh chưa; hiển thị nhãn "(đã xác minh)".
- Trang này là "bàn đạp" điều hướng sang Calendar (doc #4), Refresh demo (doc #5), và Logout.

## `sub` — vì sao là định danh đáng tin nhất

Trong các claim, `sub` (subject) là **ID ổn định & duy nhất** của người dùng tại Google. Khác với `email` (người dùng có thể đổi, hoặc email chưa xác minh), `sub`:
- Không đổi theo thời gian cho cùng một tài khoản.
- Là thứ nên dùng làm **khoá** nếu sau này lưu user vào database (thay vì dùng email).

> Trong dự án học này ta chỉ hiển thị, chưa lưu DB. Nhưng đây là lý do `AuthenticatedUser` giữ `sub` ở vị trí đầu tiên.

## Vòng đời của `oidc_user` trong session

```
   GHI:   /oidc/callback  ── sau khi verify id_token thành công
                              session.setAttribute(oidc_user, user)     (doc #3, Bước 6)

   ĐỌC:   /profile        ── ProfileController                          (doc này)

   XOÁ:   /logout         ── session.invalidate()  (xoá sạch mọi thứ)
          hoặc  /oidc/refresh khi refresh token hỏng
                             ── session.removeAttribute(oidc_user)      (doc #5, Bước 4)
```

Nghĩa là: đăng nhập xong thì `/profile` xem được; đăng xuất hoặc refresh token bị thu hồi thì `oidc_user` mất → `/profile` tự redirect về `/`.

## Ai giữ gì / dữ liệu đi đâu

```
   SESSION (server)                         Browser
   ┌───────────────────────────┐
   │ oidc_user = Authenticated  │  ──render HTML──▶  hiển thị tên/email/avatar
   │   User{sub,email,name,...} │                    (KHÔNG thấy token, KHÔNG thấy id_token)
   └───────────────────────────┘
```

Trình duyệt chỉ nhận **HTML đã render sẵn** — không hề thấy `id_token`, access token hay refresh token. Toàn bộ dữ liệu nhạy cảm ở lại server (xem doc #1 về session).

---

## Tóm tắt

1. `/profile` đọc `oidc_user` (`AuthenticatedUser`) từ session — danh tính đã verify ở callback.
2. `null` → redirect `/` (guard giống Calendar). Không gọi Google, không đụng token.
3. Đẩy `user` ra `profile.html`, hiển thị `name` / `email` (+cờ verified) / `sub` / `picture`.
4. `sub` là định danh ổn định, duy nhất — nên dùng làm khoá nếu về sau lưu DB.
5. `oidc_user`: ghi ở callback, đọc ở đây, xoá khi logout / refresh token hỏng.
