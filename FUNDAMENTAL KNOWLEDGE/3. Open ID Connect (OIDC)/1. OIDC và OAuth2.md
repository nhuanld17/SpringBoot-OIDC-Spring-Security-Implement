
## OAuth2: Authorization framework

OAuth2 **không phải** là giao thức xác thực người dùng — nó là một **authorization framework**, tức khung chuẩn hóa việc cấp quyền truy cập tài nguyên (API/resource) mà không cần chia sẻ mật khẩu. Kết quả cuối cùng OAuth2 trả về là một **Access Token** — một "chìa khóa" cho phép client gọi API để lấy hoặc thao tác dữ liệu, nhưng token này **không nói gì về danh tính người dùng**.

Ví dụ dễ hiểu: Bạn dùng app quản lý ảnh (app A) muốn truy cập ảnh trên Google Drive của bạn. OAuth2 cho phép app A xin bạn cấp quyền, rồi Google cấp một access token cho app A — token này chỉ nói "app A được phép đọc file trong Drive", không nói "đây chính là user Nguyễn Văn A".

```
┌────────┐        1. Xin quyền truy cập         ┌───────────────┐
│  App A │ ────────────────────────────────────▶│ Authorization │
│(Client)│                                      │    Server     │
│        │◀──────────────────────────────────── │  (Google)     │
└────────┘        2. Trả về ACCESS TOKEN        └───────────────┘
     │
     │ 3. Gọi API kèm access token
     ▼
┌───────────────┐
│  Resource     │   "Đây là quyền đọc Drive,
│  Server (API) │    không biết bạn là ai cụ thể"
└───────────────┘
```

## OpenID Connect: Authentication protocol xây trên OAuth2

OpenID Connect là một **giao thức xác thực (authentication protocol)**, được xây dựng ngay trên nền OAuth2, với mục tiêu xác minh danh tính (identity verification) người dùng thay vì chỉ cấp quyền try cập tài nguyên. Về mặt kỹ thuật, OIDC tái sử dụng toàn bộ luồng OAuth2 (authorization code flow) nhưng bổ sung thêm hai thứ quan trọng:

- **ID Token**: một JWT chứa thông tin xác thực danh tính người dùng (ai đăng nhập, khi nào, bằng cách nào)[okta](https://www.okta.com/identity-101/whats-the-difference-between-oauth-openid-connect-and-saml/)
    
- **UserInfo endpoint**: một API chuẩn hóa để client gọi lấy thêm thông tin hồ sơ người dùng (email, tên, ảnh đại diện...) bằng access token

```
┌────────┐   1. Yêu cầu login (scope=openid)    ┌───────────────┐
│  App A │ ────────────────────────────────────▶│ Authorization │
│(Client)│                                      │ Server (OIDC) │
│        │◀──────────────────────────────────── │  (Google)     │
└────────┘   2. Trả về ID TOKEN + ACCESS TOKEN  └───────────────┘
     │
     │ 3a. Đọc ID Token (JWT) → biết ngay: "đây là email@gmail.com"
     │ 3b. (tùy chọn) Gọi UserInfo endpoint với access token
     ▼
┌───────────────────┐
│ UserInfo Endpoint │  → trả về profile: name, email, picture...
└───────────────────┘
```

## Access Token vs ID Token: khác nhau ở đâu?

Đây là điểm học viên hay nhầm nhất, nên mình tách riêng bảng so sánh.

| Tiêu chí       | Access Token                                                                                                                           | ID Token                                                                                                                                                                                 |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Mục đích       | Cấp quyền gọi API/resource [oauth](https://oauth.net/2/)                                                                               | Xác minh danh tính người dùng [okta](https://www.okta.com/identity-101/whats-the-difference-between-oauth-openid-connect-and-saml/)                                                      |
| Định dạng      | Có thể opaque hoặc JWT (OAuth2 không bắt buộc format) [devforum.okta](https://devforum.okta.com/t/confusion-about-oktas-offerings/776) | Luôn là JWT chuẩn hóa [okta](https://www.okta.com/identity-101/whats-the-difference-between-oauth-openid-connect-and-saml/)                                                              |
| Ai đọc         | Resource server (API)                                                                                                                  | Client application                                                                                                                                                                       |
| Nội dung       | Scope, quyền hạn                                                                                                                       | Claims về identity: sub, email, name, iat, exp... [spring](https://docs.spring.io/spring-security/reference/api/java/org/springframework/security/oauth2/core/oidc/package-summary.html) |
| Định nghĩa bởi | OAuth2                                                                                                                                 | OpenID Connect Core 1.0                                                                                                                                                                  |
## Tại sao cần OIDC? — Lỗ hổng logic khi dùng thuần OAuth2

Đây là phần cốt lõi giúp bạn "master" khái niệm này. OAuth2 **không định nghĩa** cách xác thực người dùng — bản thân spec OAuth2 (RFC 6749) chỉ nói về cấp quyền, không có khái niệm "ai đang đăng nhập". Trước khi có OIDC, các công ty (Facebook, Google...) từng "chế" ra cách riêng để dùng OAuth2 làm login (gọi là "Pseudo-Authentication" hoặc "OAuth for Login") — mỗi nơi làm khác nhau, không chuẩn hóa, dễ có lỗ hổng bảo mật.[oauth](https://oauth.net/2/)

Ví dụ cụ thể: "Login with Google" cần trả lời câu hỏi **"đây chính xác là ai?"** — đó là bài toán **authentication**, không phải **authorization** (chỉ hỏi "được phép làm gì?"). Nếu chỉ dùng access token của OAuth2 thuần, app A có thể gọi Google API lấy vài thông tin, nhưng không có cách chuẩn và an toàn để xác minh chắc chắn token đó thực sự đại diện cho một phiên đăng nhập hợp lệ và mới nhất.

OIDC giải quyết vấn đề này bằng cách **chuẩn hóa lớp danh tính (standardize the identity layer)** trên nền OAuth2:[developer.orange](https://developer.orange.com/resources/openid-connect-1-0/)

- Thêm ID Token (JWT) có ký số, chứa claims chuẩn (`iss`, `sub`, `aud`, `exp`, `iat`) để verify chắc chắn nguồn gốc và tính hợp lệ
    
- Thêm scope `openid` bắt buộc để kích hoạt luồng xác thực
    
- Thêm UserInfo endpoint chuẩn hóa để lấy thêm thông tin hồ sơ
    
- Thêm discovery endpoint (`.well-known/openid-configuration`) để client tự động biết cấu hình server
