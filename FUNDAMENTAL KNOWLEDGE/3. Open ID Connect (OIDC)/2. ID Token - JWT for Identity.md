## ID Token là gì

**ID Token** là một token do **Authorization Server** phát hành sau khi người dùng xác thực thành công. Nó đại diện cho **kết quả của quá trình xác thực (authentication)** và chứa các thông tin (claims) giúp client biết **ai là người vừa đăng nhập**, **việc xác thực diễn ra khi nào**, **do server nào thực hiện**, và một số thông tin hồ sơ của người dùng (nếu được cấp quyền).

ID Token là một khái niệm thuộc **OpenID Connect (OIDC)** — một layer mở rộng xây dựng trên nền OAuth 2.0 để bổ sung khả năng **xác thực danh tính (authentication)**. OAuth 2.0 gốc chỉ giải quyết bài toán **ủy quyền (authorization)**, tức cấp quyền cho client truy cập tài nguyên của người dùng, chứ không định nghĩa cách client xác minh "ai đang đăng nhập".

Trong OIDC, **ID Token được biểu diễn dưới dạng JWT (JSON Web Token)**, được ký số bởi Authorization Server để client có thể tự xác minh tính hợp lệ của token và đọc các thông tin (claims) bên trong mà không cần hỏi lại Authorization Server.

Điểm mấu chốt là: **ID Token được thiết kế cho client đọc và xác minh**, nhằm chứng minh danh tính của người dùng. Ngược lại, **Access Token được thiết kế cho Resource Server**, nhằm quyết định client có được phép truy cập tài nguyên hay không.

## Cấu trúc JWT của ID Token

Một ID Token có 3 phần, ngăn cách bởi dấu chấm: `header.payload.signature`. Ví dụ payload (đã decode):

```
┌─────────────────────────────────────────┐
│ HEADER (thuật toán ký)                  │
│   { "alg": "RS256" }                    │
├─────────────────────────────────────────┤
│ PAYLOAD (các claims - thông tin)        │
│ {                                       │
│   "iss": "https://accounts.google.com", │
│   "sub": "1234567890",                  │
│   "aud": "my-client-id",                │
│   "exp": 1735689600,                    │
│   "iat": 1735686000,                    │
│   "nonce": "random-nonce",              │
│   "email": "user@example.com",          │
│   "email_verified": true,               │
│   "name": "John Doe",                   │
│   "picture": "https://..."              │
│ }                                       │
├─────────────────────────────────────────┤
│ SIGNATURE (chữ ký số để verify)         │
└─────────────────────────────────────────┘
```

Giải thích từng claim

| Claim                      | Ý nghĩa                                                                                       | Bắt buộc?                   |
| -------------------------- | --------------------------------------------------------------------------------------------- | --------------------------- |
| `iss`                      | Issuer — server nào phát hành token (Authorization Server)                                    | Bắt buộc                    |
| `sub`                      | Subject — ID duy nhất của user tại issuer đó, dùng để định danh user.                         | Bắt buộc                    |
| `aud`                      | Audience — client nào được phép nhận token này (client_id)                                    | Bắt buộc                    |
| `exp`                      | Thời điểm token hết hạn (Unix timestamp)                                                      | Bắt buộc                    |
| `iat`                      | Thời điểm token được phát hành (issued at)                                                    | Bắt buộc                    |
| `nonce`                    | Giá trị ngẫu nhiên do client tạo, dùng để liên kết ID Token với đúng phiên đăng nhập và chống replay attack. | Bắt buộc nếu client gửi lên |
| `email`, `name`, `picture` | Thông tin hồ sơ (profile claims) — không bắt buộc theo OIDC core, tùy scope yêu cầu           | Tùy chọn                    |
| `email_verified`           | Cho biết email đã được xác minh (true/false)                                                  | Tùy chọn                    |
**Lưu ý về `nonce`:** **`nonce`** là một giá trị ngẫu nhiên do client tạo trước khi chuyển hướng người dùng đến `Authorization Server`. Sau khi người dùng xác thực thành công, `Authorization Server` sẽ đưa chính giá trị `nonce` này vào ID Token. Khi nhận được ID Token, client so sánh `nonce` trong token với giá trị đã lưu trước đó. Nếu hai giá trị không khớp, client phải từ chối token. Cơ chế này giúp đảm bảo ID Token thuộc đúng phiên đăng nhập mà client đã khởi tạo và ngăn chặn việc kẻ tấn công phát lại (replay) một ID Token hợp lệ từ lần đăng nhập khác. - **Phần này sẽ có phần riêng nói kĩ hơn**

> **Tính bắt buộc của `nonce` theo từng luồng:** Trong **Authorization Code Flow**, `nonce` trong request là **OPTIONAL** (nên gửi để chống replay, nhưng AS chỉ bắt buộc đưa vào token *nếu* client gửi lên). Tuy nhiên, trong **Implicit Flow** và **Hybrid Flow** (`code id_token`, `code id_token token`), `nonce` trong Authentication Request là **REQUIRED** — AS bắt buộc phải có và phải đưa vào ID Token. Vì vậy "bắt buộc nếu client gửi lên" chỉ đúng tuyệt đối với Auth Code Flow.

### Nguyên lý hoạt động (Dùng Authorization Code Flow)

```
   User                  Client                  Authorization Server
    │                       │                              │
    │ 1. Đăng nhập          │                              │
    │──────────────────────>│                              │
    │                       │                              │
    │ 2. Redirect + state + nonce                          │
    │                       │─────────────────────────────>│
    │                       │                              │
    │      3. User xác thực trực tiếp với AS               │
    │<──────────────────────────────────────────────────── │
    │                       │                              │
    │ 4. Redirect về kèm Authorization Code                │
    │──────────────────────>│                              │
    │                       │                              │
    │ 5. POST /token (code)                                │
    │                       │─────────────────────────────>│
    │                       │                              │
    │ 6. Trả về:                                           │
    │                       │<─────────────────────────────│
    │                       │   - ID Token (JWT)           │
    │                       │   - Access Token             │
    │                       │   - Refresh Token (nếu có)   │
    │                       │                              │
    │              7. Client VERIFY:                       │
    │                 - signature (chữ ký bằng public key) │
    │                 - iss (phải khớp issuer)             │
    │                 - aud (phải chứa client_id của mình) │
    │                 - exp (chưa hết hạn)                 │
    │                 - iat (không quá xa hiện tại)        │
    │                 - nonce (khớp giá trị đã lưu)        │
    │                 - alg (không được là "none")         │
    │                 - azp (nếu có mặt)                   │
    │                 - auth_time, acr (nếu yêu cầu)       │
    │                       │                              │
    │          8. Client biết "đây đúng là user X"         │
```

**Diễn giải luồng hoạt động:**

1. Khi người dùng chọn đăng nhập, client tạo một yêu cầu xác thực chứa các tham số như `state` và `nonce`, sau đó chuyển hướng (redirect) trình duyệt đến **`Authorization Server`**.

2. Người dùng đăng nhập và xác thực trực tiếp với **`Authorization Server`**. Nếu thành công, **`Authorization Server`** **không trả về ID Token ngay**, mà chuyển hướng người dùng trở lại client kèm theo một **Authorization Code**. *(Lưu ý: đây là đặc điểm của **Authorization Code Flow**. Ở **Implicit Flow** và **Hybrid Flow**, ID Token lại được trả về trực tiếp từ Authorization Endpoint cùng với redirect — không cần đổi code ở Token Endpoint.)*

3. Client sử dụng Authorization Code để gọi **Token Endpoint** của Authorization Server. Sau khi xác thực client và kiểm tra code hợp lệ, Authorization Server mới trả về **ID Token**, **Access Token** và có thể cả **Refresh Token**.

4. Khi nhận được ID Token, client **không tin tưởng ngay lập tức**. Thay vào đó, client sẽ xác minh chữ ký số (signature) bằng public key của Authorization Server, đồng thời kiểm tra đầy đủ các claims theo chuẩn OIDC (§3.1.3.7): `iss` (phải khớp issuer), `aud` (phải chứa `client_id` của chính nó), `exp` (chưa hết hạn), `iat` (không được phát hành quá xa thời điểm hiện tại), `nonce` (phải khớp giá trị đã lưu), `alg` (không được là `none`), và `azp`/`auth_time`/`acr` nếu có mặt hoặc được yêu cầu.

5. Chỉ khi tất cả các bước xác minh đều thành công, client mới tin tưởng nội dung của ID Token và sử dụng các claims bên trong (như `sub`, `email`, `name`) để biết chính xác người dùng vừa đăng nhập là ai.

**Điểm quan trọng**: ID Token không phải là "thông tin do client tự khai báo", mà là một bằng chứng đã được Authorization Server ký số. Nhờ có chữ ký số, client có thể tự xác minh tính hợp lệ của token và tin tưởng thông tin danh tính bên trong mà không cần gọi thêm API chỉ để hỏi "người dùng này là ai".

**Nguyên lý cốt lõi**: Client **không hỏi lại** Authorization Server "user này là ai" — mà tự **verify chữ ký JWT bằng public key** của issuer, sau đó đọc trực tiếp claims trong payload để biết danh tính. Đây chính là lý do ID Token phải là JWT có ký số — để đảm bảo tính toàn vẹn (integrity) và xác thực nguồn gốc (authenticity) mà không cần gọi thêm API nào.

> **Lưu ý quan trọng:** JWT chỉ được **ký** (signed), không được mã hóa (encrypted) theo mặc định. Phần `payload` thực chất chỉ là base64url — **bất kỳ ai có được token đều có thể decode và đọc claims bên trong**. Chữ ký chỉ chống **sửa đổi** (tamper), không chống **đọc** (confidentiality). Vì vậy: đừng đưa thông tin bí mật vào ID Token, và luôn truyền token qua kênh TLS/HTTPS.

> **Nhưng mà Client lấy Public Key ở đâu để verify ID TOKEN ??**

- Mỗi Authorization Server công khai một **OIDC Discovery Document** (`/.well-known/openid-configuration`).
- Trong tài liệu này có trường `jwks_uri`, chỉ ra nơi chứa tập hợp các **public key** của Authorization Server.
- Client tải các public key từ `jwks_uri`, thường sẽ **cache** lại thay vì tải mỗi lần đăng nhập.
- Header của JWT thường chứa một trường `kid` (**Key ID**). Client dựa vào `kid` để chọn đúng public key trong JWKS rồi mới tiến hành xác minh chữ ký.

```
Client
   │
   │ GET /.well-known/openid-configuration
   ▼
Authorization Server
   │
   │ trả về metadata
   │
   │ jwks_uri:
   │ https://www.googleapis.com/oauth2/v3/certs
   ▼
Client
   │
   │ GET jwks_uri
   ▼
Authorization Server
   │
   │ trả về danh sách Public Keys (JWKS)
   ▼
Client
   │
   │ chọn key theo "kid" trong JWT Header
   │
   │ verify Signature
```

Đây cũng là lý do bạn thường thấy trong Spring Security hoặc các thư viện OIDC chỉ cần cấu hình:

```properties
spring.security.oauth2.client.provider.google.issuer-uri=https://accounts.google.com
```

Thư viện sẽ tự:

tải Discovery Document,
lấy jwks_uri,
tải và cache JWKS,
chọn đúng key theo kid,
verify ID Token.

> **ID Token vs UserInfo Endpoint:** ID Token *có thể* chứa một vài profile claims (như `email`, `name`, `picture`) nếu được yêu cầu qua `scope`, nhưng để lấy **đầy đủ** hồ sơ người dùng, chuẩn OIDC là client dùng **Access Token** để gọi **UserInfo Endpoint** (`/userinfo`) — một Protected Resource trả về JSON chứa các claims đã được user đồng ý chia sẻ. Đừng mặc định ID Token luôn gánh toàn bộ profile.

## ID Token vs Access Token

Đây là phần **quan trọng nhất** và dễ nhầm nhất trong OIDC/OAuth2:

| Tiêu chí                           | ID Token                                                                  | Access Token                                                                                         |
| ---------------------------------- | ------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Định nghĩa trong                   | OpenID Connect    | OAuth 2.0                                      |
| Ai đọc/hiểu nó                     | **Client** (ứng dụng)                                            | **Resource Server** (API)                                                                    |
| Mục đích                           | Xác nhận danh tính user, "user này là ai và đã đăng nhập khi nào" | Cấp quyền truy cập tài nguyên/API cụ thể                 |
| Định dạng                          | Luôn là JWT        | Có thể là JWT hoặc chuỗi random, client không cần hiểu                                       |
| Được gửi đến API?                  | **Không bao giờ** gửi đến resource server                         | **Có**, gửi kèm mỗi request tới API                       |
| Client có đọc nội dung được không? | Có, để lấy thông tin user (sub, email, name...)                           | **Không nên** — client không phải audience của token này  |
Quy tắc vàng cần nhớ: _"ID Token dành cho Client để biết ai vừa đăng nhập; Access Token dành cho Resource Server để quyết định client được làm gì"_. Nếu bạn gửi ID Token đến một API để "xác thực", đó là **anti-pattern** nghiêm trọng — vì resource server không phải audience (`aud`) hợp lệ của ID Token đó.

## Ví dụ minh họa thực tế (Google Sign-In)

Giả sử bạn bấm "Đăng nhập bằng Google" trên một website:

1. Website (client) redirect bạn đến Google với một `nonce` ngẫu nhiên.
    
2. Bạn đăng nhập Google trực tiếp — client **không nhìn thấy** mật khẩu của bạn.
    
3. Google trả về ID Token với `sub: "1234567890"`, `email: "user@example.com"`, `aud: "my-client-id"`.
    
4. Website verify chữ ký, kiểm tra `aud` đúng là client_id của chính nó, `nonce` khớp — rồi hiển thị "Xin chào, John Doe" nhờ đọc claim `name` trong token.

Website **không** gửi ID Token này đến bất kỳ API backend nào để lấy dữ liệu — nếu cần gọi API (ví dụ Google Calendar API), nó phải dùng **Access Token** riêng.

## Tham số `nonce` — Giải thích chi tiết

`nonce` (viết tắt của *number used once*) là một chuỗi ngẫu nhiên, duy nhất cho mỗi lần khởi tạo đăng nhập, do **client tạo ra** trước khi redirect người dùng đến Authorization Server.

Giá trị này được gửi trong **Authorization Request** đến Authorization Server. Sau khi người dùng xác thực thành công, Authorization Server sẽ đưa chính giá trị `nonce` đó vào claim `nonce` của **ID Token** để client kiểm tra.

### Tại sao cần `nonce`?

`nonce` giải quyết hai vấn đề bảo mật cốt lõi:

1. **Chống Replay Attack (tấn công phát lại):** Ngăn kẻ tấn công tái sử dụng (replay) một **ID Token hợp lệ** đã được Authorization Server phát hành trước đó nhằm giả mạo một phiên đăng nhập mới.

2. **Liên kết ID Token với đúng phiên đăng nhập (Session Binding):** Đảm bảo ID Token mà client nhận được chính là phản hồi cho **Authorization Request** mà client vừa khởi tạo.

## Replay Attack diễn ra như thế nào?

Trước hết cần hiểu **Replay Attack** là gì.

Replay Attack là kiểu tấn công mà **kẻ tấn công không cần tạo ra một ID Token giả hay giả mạo chữ ký số**, mà chỉ đơn giản **tái sử dụng (replay) một ID Token hoàn toàn hợp lệ** đã từng được Authorization Server phát hành trước đó.

Mục tiêu của attacker là **lừa client tạo một phiên đăng nhập (authenticated session) mới** cho mình bằng danh tính của nạn nhân.

Nếu thành công, attacker sẽ có thể truy cập hệ thống với quyền của nạn nhân mà **không cần biết mật khẩu cũng như không cần đăng nhập trực tiếp với Authorization Server**.

> **Bối cảnh kịch bản:** Ví dụ dưới đây minh họa rõ nhất ở **Implicit Flow / Hybrid Flow**, nơi ID Token lộ trực tiếp trên URL redirect (front-channel) nên attacker dễ chặn bắt. Ở **Authorization Code Flow**, ID Token về qua **back-channel** (Token Endpoint) nên rủi ro lộ thấp hơn — nhưng `nonce` vẫn là hàng rào phòng thủ chuẩn và bạn nên luôn gửi nó (xem bảng tính bắt buộc ở dưới).

### Ví dụ

Giả sử người dùng **Alice** đăng nhập vào website bằng Google.

```
Alice                    Client (Website)                Google
  │                              │                         │
  │ 1. Bấm "Đăng nhập"           │                         │
  │─────────────────────────────>│                         │
  │                              │ 2. Redirect sang Google │
  │                              │────────────────────────>│
  │                              │                         │
  │<────────── Đăng nhập Google ──────────────────────────>│
  │                              │                         │
  │                              │  
  │                              │ 3. Đổi Authorization    │
  │                              │    Code lấy ID Token    │
  │                              │────────────────────────>│
  │                              │                         │
  │                              │<────────────────────────│
  │                              │  ID Token (JWT)         │
  │                              │  sub = alice            │
  │                              │  signature = ✔          │
  │                              │                         │
  │                              │ 4. Verify thành công    │
  │                              │ → Tạo Session cho Alice │
```

Client kiểm tra:

- ✔ Chữ ký (`signature`) hợp lệ.
- ✔ `iss` đúng.
- ✔ `aud` đúng.
- ✔ Token chưa hết hạn (`exp`).

Do đó, website tin rằng **Google vừa xác thực Alice** và tạo một phiên đăng nhập (session) cho cô ấy.

Giả sử sau đó, bằng một cách nào đó (ví dụ log bị lộ, XSS, malware hoặc dump bộ nhớ), **attacker lấy được chính ID Token này**.

Một thời gian sau, attacker muốn **đăng nhập trái phép vào tài khoản của Alice** mà không cần đăng nhập qua Google.

Thay vì thực hiện lại toàn bộ quy trình đăng nhập, attacker sẽ **gửi lại (replay)** chính ID Token cũ mà mình đã đánh cắp, với hy vọng website sẽ tin rằng:

> "Đây là ID Token vừa được Google phát hành cho lần đăng nhập hiện tại."

```
             ID Token cũ (được Google phát hành trước đó)

Attacker                                 Client (Website)
    │                                            │
    │  Replay ID Token                           │
    │───────────────────────────────────────────>│
    │                                            │
    │  signature = ✔                             │
    │  iss = ✔                                   │
    │  aud = ✔                                   │
    │  exp = ✔                                   │
    │                                            │
    │  ❓ Website có tạo Session mới             │
    │     và đăng nhập Attacker thành Alice?     │
```

Nếu client chỉ kiểm tra:

- chữ ký (`signature`)
- `iss`
- `aud`
- `exp`

thì **ID Token vẫn hoàn toàn hợp lệ**, vì đúng là token do Google phát hành.

Tuy nhiên, chữ ký số chỉ chứng minh rằng:

> **"Đây là ID Token thật do Authorization Server phát hành."**

Nó **không chứng minh** rằng:

> **"Đây là ID Token vừa được Authorization Server phát hành cho phiên đăng nhập hiện tại."**

> **Tại sao các claim thời gian (`iat`, `exp`) không đủ?** Ngay cả khi client kiểm tra `iat` (thời điểm phát hành) và `exp` (hết hạn), attacker vẫn có thể replay ID Token **trong cửa sổ hiệu lực** (thường vài phút đến 1 giờ). `iat` chỉ cho biết "token được phát hành lúc nào", chứ không nói "có phải dành cho phiên đăng nhập này không" — nên một mình `iat` không ngăn được replay. Đó là lý do `nonce` (giá trị duy nhất cho mỗi phiên) là mảnh ghép còn thiếu.


Nói cách khác, client **không thể biết**:

- Đây là ID Token vừa được phát hành cho **lần đăng nhập hiện tại**, hay
- Chỉ là **một ID Token cũ** mà attacker đang phát lại (replay).

Đây chính là lý do **`nonce`** được đưa vào OpenID Connect.

---

## `nonce` ngăn chặn Replay Attack như thế nào?

Như đã phân tích ở phần trước, vấn đề của client là **không thể phân biệt** giữa:

- Một **ID Token vừa được Authorization Server phát hành** cho phiên đăng nhập hiện tại.
- Một **ID Token cũ** bị attacker đánh cắp rồi phát lại (replay).

Đây chính là bài toán mà **`nonce`** được thiết kế để giải quyết.

Ý tưởng của `nonce` rất đơn giản:

- Mỗi lần bắt đầu một phiên đăng nhập mới, client sẽ sinh một **giá trị ngẫu nhiên, duy nhất** (`nonce`).
- Giá trị này được gửi kèm trong **Authorization Request** đến Authorization Server.
- Sau khi xác thực người dùng, Authorization Server sẽ đưa chính giá trị `nonce` đó vào **claim `nonce` của ID Token**.
- Khi nhận được ID Token, client chỉ cần so sánh `nonce` trong token với `nonce` mà mình đã lưu trước đó.
  - Nếu **khớp**, chứng tỏ ID Token được phát hành cho đúng phiên đăng nhập hiện tại.
  - Nếu **không khớp**, client sẽ từ chối token vì rất có thể đó là một ID Token của phiên đăng nhập khác đang bị phát lại (replay).

Quá trình này được minh họa như sau.

Mỗi lần bắt đầu một phiên đăng nhập mới, client sẽ sinh một giá trị ngẫu nhiên mới, ví dụ:

```
nonce = A1B2C3
```

Client gửi giá trị này trong **Authorization Request**.

```
Client                                   Authorization Server
   │                                              │
   │ Authorization Request                        │
   │ nonce = A1B2C3                               │
   │─────────────────────────────────────────────>│
```

Sau khi người dùng xác thực thành công và client đổi Authorization Code lấy token, Authorization Server sẽ đưa chính giá trị này vào claim `nonce` của ID Token.

```json
{
    "sub": "alice",
    "nonce": "A1B2C3"
}
```

Client đọc claim `nonce` trong ID Token rồi so sánh với giá trị đã lưu trước khi redirect.

```
nonce trong ID Token

A1B2C3

==

nonce đã lưu

A1B2C3

✔ Khớp → Chấp nhận
```

Giả sử vài giờ sau website bắt đầu **một phiên đăng nhập hoàn toàn mới**.

Lần này client sẽ sinh một `nonce` khác.

```
nonce = X9Y8Z7
```

Trong khi attacker chỉ có ID Token cũ.

```json
{
    "sub": "alice",
    "nonce": "A1B2C3"
}
```

Website kiểm tra:

```
nonce trong ID Token

A1B2C3

==

nonce của phiên đăng nhập hiện tại

X9Y8Z7

❌ Không khớp → Reject
```

Mặc dù:

- ✔ Chữ ký vẫn hợp lệ.
- ✔ `iss` đúng.
- ✔ `aud` đúng.
- ✔ Token chưa hết hạn.

Client **vẫn phải từ chối ID Token**, vì nó **không được phát hành để trả lời Authorization Request của phiên đăng nhập hiện tại**.

Đây chính là ý nghĩa của **Session Binding** trong OpenID Connect.

`nonce` giúp client chứng minh rằng:

> **ID Token mình vừa nhận được chính là phản hồi cho Authorization Request mà mình đã khởi tạo**, chứ không phải một ID Token cũ đang bị attacker phát lại.


### Cách client sinh và lưu `nonce` (thực tế)

- **Sinh:** Dùng bộ sinh số ngẫu nhiên mật mã (cryptographically secure random) với đủ entropy để attacker không thể đoán được (theo OIDC Core §15.5.2). Ví dụ trong Node.js:

```js
crypto.randomBytes(16).toString("hex")
```

- **Lưu tạm:** Trước khi redirect, client lưu `nonce` vào nơi gắn với phiên đăng nhập hiện tại. Với server-side web application, giá trị này thường được lưu trong **HTTP Session** hoặc **HttpOnly Cookie**. Với browser-based application (SPA), `nonce` có thể được lưu trong **sessionStorage** hoặc cơ chế lưu trữ phù hợp khác.

- **So sánh:** Khi nhận được ID Token, client đọc claim `nonce` rồi đối chiếu với giá trị đã lưu trước đó. Nếu không khớp, client **phải từ chối toàn bộ ID Token**, ngay cả khi chữ ký vẫn hợp lệ.

### Tính bắt buộc của `nonce` theo từng luồng

| Luồng (Flow)                          | `nonce` trong request | Bắt buộc trong ID Token?                          |
| ------------------------------------- | --------------------- | ------------------------------------------------- |
| **Authorization Code Flow** (`code`)  | OPTIONAL              | Chỉ nếu client gửi lên (AS MUST đưa vào token)    |
| **Implicit Flow** (`id_token`, `id_token token`) | REQUIRED              | Bắt buộc                                          |
| **Hybrid Flow** (`code id_token`, `code id_token token`) | REQUIRED              | Bắt buộc                                          |
| **Hybrid Flow** (`code token`)        | OPTIONAL              | Chỉ nếu client gửi lên (AS MUST đưa vào token)   |

> **Lưu ý:** Dù ở Auth Code Flow `nonce` là tùy chọn, bạn **nên luôn gửi** nó — đây là hàng rào chống replay đơn giản và chuẩn nhất mà không tốn thêm chi phí.
>
> **Chi tiết theo OIDC Core §3.3.2.1 (Hybrid Flow Authentication Request):** Quy định chính xác là — *"nonce REQUIRED if the Response Type of the request is `code id_token` or `code id_token token` and **OPTIONAL when the Response Type of the request is `code token`**"*. Nói cách khác, spec **không** gộp mọi Hybrid vào "REQUIRED"; riêng `code token` được phép OPTIONAL. Lý do: ở `code token`, ID Token không bao giờ trả về qua front-channel (chỉ có `code` + `access_token`), nên rủi ro lộ ID Token thấp, giống Auth Code Flow. Dù vậy, nếu client có gửi `nonce` trong request, Authorization Server **bắt buộc** phải đưa claim `nonce` vào ID Token (§3.3.2.11).

### `nonce` khác `state` như thế nào?

Nhiều người hay nhầm `nonce` với `state` vì cả hai đều là giá trị ngẫu nhiên client tạo. Điểm khác biệt then chốt:

| Tiêu chí      | `state`                                    | `nonce`                                              |
| ------------- | ------------------------------------------ | ---------------------------------------------------- |
| Mục đích      | Chống **CSRF** — liên kết request/response | Chống **replay** + gắn ID Token vào đúng session     |
| Xuất hiện ở   | Chỉ trong URL redirect/callback            | Trong URL request **và** claim bên trong ID Token    |
| Bên verify    | Client đối chiếu `state` trả về == `state` gửi đi | Client đối chiếu claim `nonce` trong token == giá trị đã lưu |
| Chuẩn         | OAuth 2.0 (RECOMMENDED)                    | OpenID Connect (bắt buộc ở Implicit/Hybrid)          |

Tóm lại: `state` bảo vệ **kênh redirect** khỏi CSRF, còn `nonce` bảo vệ **tính xác thực của ID Token** khỏi replay. Một luồng OIDC đúng chuẩn nên dùng **cả hai**.
